# 文脈経済（Context Economy）

トークン上限（rate-cap）の中で**精度を落とさず長く稼働**するための運用規律。
背景・原則の根拠は ADR-0023。抽象原則（DRY 等）は brain、行数予算・compact 閾値は `context-management.md` を参照。本ファイルは「呼び出しごとの文脈衛生」に絞る。

> グレード: **GUIDE**（§6 の聖域のみ HARD = 既存 HARD 規則に従う）。

## 1. per-call context hygiene — 不要な文脈を渡さない（最優先）

モデル / subagent を呼ぶたび、**そのタスクに必要なものだけ**渡す。汚染（無関係文脈）はコストと精度を同時に悪化させる。

- subagent には「対象ファイル・差分・タスク」だけを scoped に渡す。リポ全体を読ませない。
- 読み取り専用の探索は `Explore` / `Plan`（CLAUDE.md を読み込まない軽量型）を選ぶ。`general-purpose` は重い前提を背負うので必要時のみ。
- 子の生探索（全文・全ログ・思考過程）を親に戻さない。**Return Contract** で `verdict + 該当行 + 1行根拠` に圧縮して返す（出力側 contract）。
- コードは全文再掲しない。load-bearing な断片のみ（snippet-on-demand）。
- 出力は結論ファースト・diff 主体。冗長な前置き・全文ダンプを避ける（出力は高単価）。

## 2. cache を壊さない

- **model / effort はセッション（自律では各サイクル）の頭で固定**。途中変更は cache 全破棄 → full reprocess。
- fan-out は**セッション前半 / compact 直後**（親が小さいうち）に起動する。
- 同等タスクを複数本走らせる時は named subagent でなく **fork**（親 cache を継承し初回が大幅に安い）。
- 安定する文脈（CLAUDE.md・rules・差分コンテキスト）は前方に、可変部は後方に。

## 3. 文脈は資産でなく負債

- 既定は **retrieve > resident**。常駐は例外で、足す時は「なぜ常駐が必要か」を言えること。
- **Read-once**: 一度読んだファイルを再読込しない（harness が編集成否を返す。検証のための再読は不要）。
- 常駐は索引（リンク）だけ、本体は呼び出し時にロード（階層化）。

## 4. 長時間・自律稼働（詳細は PR2 の自律ループ ADR）

- セッション ~60% で**先回り `/compact`**（auto の 80% を待たない）。早いほど working context を温存できる。
- 自律ループは状態を会話に溜めず **disk の ledger**（決定 + why / 残タスク / 次の一手）に書き、サイクル境界で context をリセットする。

## 5. fan-out は難所だけ（trivial-gating）

- trivial / doc-only / 小変更は single-thread で処理。多エージェント fan-out を発火させない。
- 決定的検査（typecheck / lint / fitness）を LLM の前に置き、機械で分かることは LLM に判定させない。
- ただし**縮退の根拠**であって観点の無条件 skip ではない（§6・決定的に判定できない設計/仕様観点は残す）。

## 6. 削らない核（聖域・HARD）

トークン効率を理由に**省略してはならない**:

- HARD 安全ルール・本番保護・不可逆操作のガード（enforcement 層を含む）
- 設計判断の「なぜ」・暗黙の前提（DB 接続先等）
- DB / API / 破壊的変更に対する必須レビュー観点（温度感・予算より優先）

## 7. lossy 機構には検知層

- 要約 / compaction / 観点縮退で**落としたものは silent drop 禁止**。Issue or ledger に「未検査・未反映」として明示し、後で回収できるようにする。
- 縮退の発火条件（残 cap・難易度）と結果はログに残す。

## 8. 難所の閉集合（R2）と model tiering（既定は精度優先）

以下のいずれかに該当する作業は**難所**。**該当するか判定に迷う場合も難所として扱う（上位既定）**:

1. **設計判断** — 複数案の裁定 / データモデル・スキーマ変更 / API 契約の変更
2. **root-cause 分析** — 再現不能・間欠・並行性・環境依存のバグ
3. **矛盾裁定** — レビュー観点間 / 仕様と実装 / ADR と diff の矛盾の解決
4. **セキュリティ** — 認可・信頼境界・入力検証・ガード機構の変更
5. **最終 judge** — マージ可否 / リリース可否 / 無人続行可否の裁定

**難所での動作（不変条件）**:

- 単発判断を禁止し、**敵対検証（R3・下記）を必ず発火**してから結論を出す。**必ず上位モデル**を使う。
- budget-gate THROTTLE 時は検証の**票数のみ縮退**し、縮退した事実を **ledger に記録**する（silent drop 禁止・§7）。幅は削っても正しさは削らない（§6 聖域）。

**R3 敵対検証の定型**（いずれか1つ以上を実行）: ①**反証プロンプト**「この結論を落とす理由を1つ挙げよ。挙がらなければ確認した根拠を1行で示せ」 ②**premise-check**「前提の事実を3つ列挙し各々を当該セッションで確認したか YES/NO」 ③**消失テスト**（削除・統合・縮退時）「この変更で消える検証が過去に捕まえた問題を挙げよ。挙がらないと確認してから進める」。

**model tiering**:

- 既定はモデルを下げない。明確に機械的なサブタスク（列挙・検索・整形）に限り下位モデル可。難所は上記のとおり必ず上位モデル。
- 効果は `/token-audit` で**実測してから**。未実測の一律ダウングレードはしない。
