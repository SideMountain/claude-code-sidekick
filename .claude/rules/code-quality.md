# コード品質（GUIDE グレード）

文脈に応じて判断してよい。レビュー時（/review-code）のチェック観点として機能する。
抽象的な判断原則（DRY、影響範囲の先読み等）は個人 brain（`~/.claude/brain/thinking.md` §1、初期テンプレートは sidekick の `brain/thinking.md`）を参照。本ファイルは具体的なコーディング実践に絞る。

---

## 1. Surgical Changes — 変更はリクエストに紐づく範囲だけ

- **変更した全行が「なぜ変えたか」を説明できる状態にする**
- 隣接するコード・コメント・フォーマットを「ついでに」改善しない
- 既存のコードスタイルに合わせる。自分の好みではなく、リポジトリの慣習に従う
- 無関係なデッドコードを見つけたら、削除ではなく報告する
- リファクタリングと機能変更を同じコミットに混ぜない

## 2. 簡潔さ — 最小限のコードで意図を表現する

- 1箇所でしか使わないコードに汎用的な抽象化を作らない
- 起こりえない内部分岐のエラーハンドリングは書かない（システム境界のバリデーションは必要）
- 意図が伝わる簡潔なコードを書く。冗長よりも簡潔を選ぶ
- ただし、可読性を犠牲にした過度なワンライナー化はしない
- テスト: 「シニアエンジニアが見て、過剰に複雑だと言わないか？」

## 3. 構造 — 読みやすさと保守性のバランス

- メソッドは1つの機能単位に分割する。「何をしているか」が名前で伝わるサイズ
- ネストが深くなったら早期 return やメソッド抽出で平坦化を検討する
- if / for / ラムダ式は場面に応じて使い分ける。可読性が判断基準
- ファイルが肥大化したら責務で分割する。行数の絶対上限ではなく、凝集度で判断
- 意図が自明でないコードには「なぜ」のコメントを書く。「何をしているか」のコメントは不要

## 4. 定数と共通化 — 修正漏れを構造で防ぐ

- マジックナンバー・マジックストリングを使わない。意味のある名前の定数にする
- 同じ処理パターンが3回出たら共通化を検討する（Date フォーマット、バリデーション等）
- 定数の配置はプロジェクトの慣習に従う。定数クラスに集約するか使用箇所の近くに置くかはPJ判断

## 5. セッション間の一貫性 — AI 固有の注意点

- コードを書く前に、同一ファイル・同一モジュールの既存パターンを検出して従う
- 前のセッションが作ったコードを「自分ならこう書く」で書き直さない
- 設計意図が分からないコードをリファクタリングする前に、意図を確認する

## 6. 自己検証 — 「動く」ではなく「証明できる」

- タスクを受けたら、完了条件を具体化する（「バグ修正」→「再現テストを書いて通す」）
- 複数ステップのタスクは、各ステップに検証ポイントを置く
- 曖昧な完了条件（「いい感じにして」）は、具体化を提案してから着手する
