# 実装品質レビュー（/review-code）

## 実行方式

このスキルは **Agent ツールで隔離実行する**。
`/review` オーケストレーターから呼ばれる場合も、単体で呼ばれる場合も同様。

1. Agent ツールを起動し、このスキルの全手順（Step C1〜C7）を渡す
2. Agent はスキルの手順を実行し、Return Contract に従って結果を返す
3. メインコンテキストには判定結果と指摘サマリのみが残る

## 目的

変更内容が「正しく作られているか」を検証する。
仕様の妥当性ではなく、**コードの品質・整合性・安全性**にフォーカスする。

## 前提

- `git diff` でベースブランチからの変更内容を把握してから開始する
- 変更ファイルだけでなく、影響を受ける周辺コードも読む

## 手順

以下のステップを**順番に**実行し、各ステップの結果を報告する。

### Step C1: CLAUDE.md ルール違反チェック

プロジェクトルールに違反していないか確認する。

- [ ] コミットメッセージがプロジェクトの規約に準拠しているか
- [ ] DB操作前に接続先確認を実行したか（DB使用プロジェクトの場合）
- [ ] 保護ブランチに直接コミットしていないか
- [ ] Worktree ルールに準拠しているか（Worktree 運用プロジェクトの場合）
- [ ] 命名規則に準拠しているか
- [ ] CLAUDE.md に定義されたプロジェクト固有ルールに違反がないか

### Step C2: コード整合性・一貫性

プロジェクト全体のパターンと整合しているか確認する。

- [ ] **変更ファイルが実際に使用されているか**: 変更・新規作成したファイルが、どこかから `import` されているか確認する。特に新規作成ファイルやリファクタで分離したファイルは要注意

```bash
# 変更ファイルがimportされているか確認（各ファイルに対して実行）
# フレームワークが自動読み込みするファイル（page.tsx, route.ts 等）は除外
grep -r "ファイル名（拡張子なし）" --include="*.ts" --include="*.tsx" --include="*.js" --include="*.jsx" -l src/ app/ lib/ components/ 2>/dev/null
```

- [ ] 既存コードのパターン（エラーハンドリング、レスポンス形式、ログ出力）と一致しているか
- [ ] 同種の機能が既にある場合、そのパターンに従っているか
- [ ] `import` パスのエイリアスルール（`@/` 等）に準拠しているか

### Step C3: 拡張性・保守性

将来の変更に耐えられる設計か確認する。

- [ ] ハードコード値が定数化されているか（マジックナンバー検出）

```bash
# 条件分岐内の数値リテラルを検出
git diff HEAD~1...HEAD -- 'src/' 'app/' 'lib/' | grep '^+' | grep -v '^+++' | grep -E '(if\s*\(|[?:])' | grep -E '[^a-zA-Z_\.][0-9]{2,}[^a-zA-Z_]'
```

除外: 0, 1, -1, 100, HTTPステータス(200,400,401,403,404,500), 定数定義ファイル, テストファイル, コメント行

- [ ] 同一構造のリテラル（ラベルマップ等）が複数箇所に散在していないか
- [ ] 過度な抽象化をしていないか（YAGNI: 使わない汎用性は不要）
- [ ] 認知的複雑性: 関数の分岐が多すぎないか（目安: 1関数15行以内、ネスト3段以内）

### Step C4: DB設計ベストプラクティス

ORM スキーマやマイグレーションに変更がある場合に実行する。ORM を使わないプロジェクトではスキップ。

- [ ] **正規化**: 冗長データがないか、適切なリレーションが定義されているか
- [ ] **インデックス**: 頻出クエリの WHERE / ORDER BY にインデックスが設定されているか
- [ ] **NULL戦略**: NULL許容 vs デフォルト値の選択が適切か
- [ ] **命名**: テーブル名・カラム名がプロジェクトの命名規則に準拠しているか
- [ ] **Enum設計**: 状態管理は Enum で表現されているか、将来の状態追加に耐えられるか
- [ ] **外部キー制約**: `onDelete` の振る舞いが適切か（Cascade vs Restrict vs SetNull）
- [ ] **マイグレーション破壊性**: 破壊的キーワード（DROP, ALTER TYPE, RENAME, NOT NULL追加）がないか
  - 破壊的の場合: Expand-Contract パターンが必要

### Step C5: 水平展開調査

変更箇所と同種のコードに同じ問題がないか調査する。

**手法:**

1. 変更の「パターン」を抽出する（例: 「バリデーション強化」「エラーハンドリング追加」）
2. 同じパターンが必要な箇所を `grep` / `Glob` で網羅的に検索
3. 漏れている箇所があれば指摘

- [ ] 変更と同種のロジックが他に存在するか確認
- [ ] 存在する場合、同じ修正が必要か評価
- [ ] 不変条件に関わる変更の場合、**全制御パスを機械的にスキャン**

### Step C6: セキュリティ・パフォーマンス

**セキュリティ（OWASP Top 10 + ADR-0002 Layer 3）:**

- [ ] **入力バリデーション**: ユーザー入力が適切にバリデーションされているか
- [ ] **認証・認可**: API ルートに適切な認証チェックがあるか。認証バイパスの可能性はないか
- [ ] **インジェクション**: 生SQL や動的クエリ組み立てがないか
- [ ] **XSS**: ユーザー入力をそのまま HTML に埋め込んでいないか
- [ ] **CSRF**: 状態変更エンドポイントに CSRF 対策があるか
- [ ] **データ露出**: APIレスポンスに不要なフィールド（内部ID、他ユーザー情報）が含まれていないか
- [ ] **セキュリティ領域判定**: この変更は認証・認可・個人情報・決済・インフラに触れるか？
  → 触れる場合、`[needs-security-review]` フラグを立てて報告する

**パフォーマンス:**

- [ ] **N+1クエリ**: ループ内で DB クエリを発行していないか
- [ ] **並列化**: 独立したクエリ・API呼び出しが並列化されているか
- [ ] **データ取得の最小化**: 必要なフィールドのみ取得しているか

### Step C7: 越境チェック（→ test, → ops）

実装観点から隣接領域に踏み込んで確認する。

- [ ] **→ test**: コードが露呈するエッジケース（null、空配列、境界値）にテストがあるか
- [ ] **→ ops**: エラー時のログ出力・監視が十分か

## Gotchas

このセクションは実運用で蓄積した「引っかかりやすいポイント」を記録する。

- **C2 false positive: フレームワーク自動読み込みファイル** — Next.js の `page.tsx`, `route.ts`, `layout.tsx` 等はどこからも明示的に import されないが、フレームワークが自動的にロードする。「未使用ファイル」として誤検出しないこと
- **C3 マジックナンバー除外対象** — HTTP ステータスコード（200, 400, 401, 403, 404, 500）、配列インデックス（0, 1, -1）、パーセント（100）は定数化不要。テストファイル・コメント行も除外対象
- **CLEAN_CMD パターン** — guard-bash.sh はクォート文字列と HEREDOC を除去して判定する（`gh pr create --body "...git push..."` のような false positive を防ぐ）。レビュー時に同様の引用内パターンに注意
- **C5 水平展開の過剰適用に注意** — 「同じパターンだから全箇所に適用すべき」と安易に判断しない。各箇所のコンテキスト（エラーの発生確率、ユーザー影響度）が異なる場合がある

## 出力フォーマット

```
=== 実装品質レビュー結果 ===

[C1: ルール違反] OK / NG
  （NGの場合: 違反内容と修正方法）

[C2: 整合性] OK / 要修正
  （要修正の場合: 不整合箇所の指摘）

[C3: 拡張性] OK / 要改善
  C3a. マジックナンバー: なし / 検出箇所
  C3b. リテラル重複: なし / 検出箇所
  C3c. 認知的複雑性: OK / 要分割

[C4: DB設計] 対象外 / OK / 要改善
  （要改善の場合: 指摘事項）

[C5: 水平展開] 漏れなし / 漏れあり
  （漏れありの場合: 同種の修正が必要な箇所リスト）

[C6: セキュリティ・パフォーマンス] OK / 要対応
  （要対応の場合: リスク項目と対応方法）

[C7: 越境チェック]
  → test: OK / 指摘あり
  → ops: OK / 指摘あり

総合判定: コミット可 / 修正必要 / ユーザー確認必要
  （指摘事項のサマリ）
```

---

## Return Contract

### 返すもの
- 出力フォーマットに従った判定結果（各Step の OK/NG + 指摘事項サマリ）
- 総合判定（コミット可 / 修正必要 / ユーザー確認必要）

### 返さないもの
- grep / git diff の生出力
- コード調査の途中経過（「このファイルを読んだ」「この関数を確認した」等）
- チェック項目ごとの詳細な調査ログ（結果のみ報告）
