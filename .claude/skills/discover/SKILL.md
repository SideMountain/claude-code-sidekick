# /discover — アイデアから要件を掘り起こす

## 目的

ユーザーの「こういうことがしたい」を、**現状調査 → ヒアリング → ギャップ分析 → 選択肢提示 → タスク分解**の順で構造化する。

`/auto-implement` が「設計確定済み → 実装」を担うのに対し、`/discover` は「アイデア → 設計確定」を担う。壁打ちの入口を構造化するスキル。

## いつ使うか

- 「○○がしたい」「○○って出来る？」のように、ゴールはあるが具体的な仕様がまだない
- 既存実装の全体像を把握してから設計を議論したい
- タスクに分解したいが、どこから手をつけるか分からない

## いつ使わないか

- 仕様が確定していて実装するだけ → `/auto-implement`
- バグ報告で原因調査が必要 → 直接調査
- 壁打ち中に「これでいこう」と決まった → `/record-decision` + 実装着手

---

## 手順

### Step 1: 現状調査ファースト

**ユーザーに質問する前に、自分で調べられることを全て調べる。**
（thinking.md セルフレビュー Step 1 と同じ原則）

```
調査対象:
- アイデアに関連するコード・ファイル（Grep/Glob で探索）
- 既存の設計判断（docs/decisions/*.md）
- 関連する GitHub Issues（open/closed 両方）
- MEMORY.md のバックログ（同趣旨の項目がないか）
- CLAUDE.md の設定・ルール（制約条件）
```

調査結果を**先にユーザーに共有**する:

```
=== 現状調査結果 ===

関連する既存実装:
  - path/to/file.ts: ○○の処理（L10-50）
  - path/to/other.ts: △△のロジック

関連する設計判断:
  - ADR-0003: □□の理由で◇◇を採用

関連する Issue / バックログ:
  - #15: 類似の要望（closed、○○で対応済み）
  - Backlog: 「△△の改善」（未着手）

制約条件:
  - STG_ENABLED=false → 2段階リリース不要
  - ORM_TYPE=prisma → マイグレーション考慮が必要
```

### Step 2: ヒアリング（構造化された質問）

現状調査の結果を踏まえて、**足りない情報だけ**を聞く。
調査で分かったことを再度聞かない。

**質問の構造:**

1. **ゴールの確認**: 「○○がしたい」の「○○」をもう一段具体化
   - 「誰が」「どの場面で」「何ができるようになる？」
2. **スコープの確認**: 今回のスコープと、今回やらないこと
   - 「これは今回含みますか？」「ここまでは次回でいい？」
3. **制約の確認**: 技術的制約、スケジュール、優先度
   - 「いつまでに？」「既存の○○との互換性は必要？」

**ヒアリングのルール:**
- 一度に聞くのは **3問以内**。大量の質問を一気に投げない
- 選択肢を提示する（「A と B どちらに近いですか？」）
- 「分からない」「後で決める」も有効な回答として受け入れる
- 調査で判明した情報は前提として提示し、確認だけ求める

### Step 3: ギャップ分析

現状（Step 1）とゴール（Step 2）の差分を整理する。

```
=== ギャップ分析 ===

ゴール: （Step 2 で確認した内容）

現状 → ゴール のギャップ:
  1. ○○が存在しない → 新規作成が必要
  2. △△は既存だが □□が不足 → 拡張が必要
  3. ◇◇は既存でそのまま使える → 変更不要

影響範囲:
  - 変更が必要なファイル: （一覧）
  - 影響を受ける既存機能: （あれば）
  - DB変更: あり / なし
```

### Step 4: 選択肢提示

**先に仕様セルフレビュー**（thinking.md §2「提案前チェック」の項目3-5 に準拠、Step 4 に進む前にチェック）:
- [ ] 過去の却下理由（`memory/feedback_*.md`）と矛盾しないか
- [ ] 「やらなくていいもの」が混じっていないか
- [ ] ユーザー影響・運用影響の観点は抑えられているか

懸念があれば Step 1 の調査に戻る。固まったら以下を実施する。

ギャップを埋める方法が複数ある場合、比較表で提示する。
thinking.md §1 の判断原則で各案を評価する。

**推奨を確定する前に（R3 反証・context-economy §8 L1）**: 「この推奨案を落とす理由を 1 つ挙げよ。挙がらなければ、それを確認した根拠を 1 行で示せ」を自問する。落とす理由が挙がれば比較表（省略時は却下理由の記載）に反映してから推奨を出す（挙がらないことの確認を経ずに推奨を確定しない）。

```
=== 選択肢 ===

| | A案: ○○ | B案: △△ | C案: □□ |
|---|---|---|---|
| 概要 | ... | ... | ... |
| メリット | ... | ... | ... |
| デメリット | ... | ... | ... |
| 工数目安 | 小 | 中 | 大 |
| 判断原則との整合 | ○○ファーストに合致 | △△の懸念あり | — |

推奨: A案（理由: ...）
```

**比較表の省略条件**（以下のいずれかを満たす場合のみ）:
1. 技術的に選択肢が1つしかない（他の案が実装不可能）
2. 既存 ADR / thinking.md §1 の判断原則と一意に整合する（他の案は原則違反）
3. 工数差が桁違いで、他案を選ぶメリットが存在しない

省略する場合も、**却下した案とその理由は必ず明示する**（thinking.md §1「却下した案は『なぜ外したか』の理由もセットで出す」）。迷ったら省略しない。

**ここでユーザーの判断を待つ。** 勝手に決めない。

### Step 5: タスク分解

**先に仕様セルフレビュー**（thinking.md §2「提案前チェック」の項目4「一貫性チェック」に準拠、タスク分解に進む前にチェック）:
- [ ] 選択した案が thinking.md §1 判断原則と一貫しているか
- [ ] スコープが Step 2 で確認した範囲内か（膨らんでいないか）

ユーザーが方向性を承認したら、実行可能なタスクに分解する。
分解の粒度・完了条件の書き方は `references/task-breakdown-examples.md`（OK/NG 例）に従う。

```
=== タスク分解 ===

選択: A案（○○）

タスク一覧:
  1. □□の追加（ファイル: path/to/file.ts）
     - 完了条件: ○○ができること
     - DB変更: なし
  2. △△の修正（ファイル: path/to/other.ts）
     - 完了条件: △△が○○に対応すること
     - DB変更: あり（マイグレーション必要）
  3. テスト追加
     - 完了条件: 新機能のハッピーパス + エッジケース

推奨実行順: 2 → 1 → 3（DB変更を先にマージ）

─────────────────
GitHub Issue に起票しますか？
それとも今からこのまま実装しますか？
```

### Step 6: 次のアクション

ユーザーの選択に応じて:

- **Issue 起票**: `gh issue create` でタスクごとに Issue を作成
- **即実装**: Worktree を作成して着手（`/auto-implement` に渡せる粒度なら提案）
  - 仕様の妥当性は Step 4-5 のセルフレビューで検証済み。実装後は `/review` でコード品質を確認してから PR を作成する
- **ADR 記録**: 設計判断があれば `/record-decision` を提案
- **保留**: MEMORY.md バックログに記録

---

## Gotchas

- **Step 1 を飛ばさない**: ヒアリングから始めると「聞いてから調べる」になり、ユーザーの時間を無駄にする。調べてから聞く
- **壁打ちモードに入らない**: `/discover` は構造化が目的。議論が発散したら「一旦 Step 3 に戻りましょう」と収束させる
- **スコープを広げすぎない**: ユーザーが「ついでに○○も」と言った場合、「今回のスコープに含めますか？ 別タスクにしますか？」と明示的に確認する
- **Step 4 の比較表を勝手に省略しない**: 省略は Step 4 に記載した3条件のいずれかを満たす場合のみ。「推奨案がある」だけでは省略理由にならない
- **セルフレビューを飛ばさない**: Step 4・Step 5 冒頭のチェックは構造的に必須。懸念が残った状態で先に進まない
- **NOTION_ENABLED=true の場合**: タスクDBへの起票も選択肢に含める
