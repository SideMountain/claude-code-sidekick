# 運用・耐障害性レビュー（/review-ops）

## 実行方式

このスキルは **Agent ツールで隔離実行する**。
`/review` オーケストレーターから呼ばれる場合も、単体で呼ばれる場合も同様。

1. Agent ツールを起動し、このスキルの全手順（Step O1〜O7）を渡す
2. Agent はスキルの手順を実行し、Return Contract に従って結果を返す
3. メインコンテキストには判定結果と指摘サマリのみが残る

## 目的

変更内容が「本番で安全に動き続けられるか」を検証する。
機能の正しさではなく、**運用時の安全性・検知可能性・回復可能性**にフォーカスする。

## 前提

- `git diff` でベースブランチからの変更内容を把握してから開始する
- 本番環境の構成（ホスティング、DB、外部サービス）を CLAUDE.md で確認する

## 手順

以下のステップを**順番に**実行し、各ステップの結果を報告する。

### Step O0: PJ固有チェックの読み込み

このスキルと同階層の `references/` 配下にPJ固有のチェックファイルがあれば読み込む。
以降のステップに加えて、PJ固有チェックも実行する。

> ファイルがなければこのステップはスキップ。

### Step O1: 障害モード分析

外部依存が失敗した場合の振る舞いを確認する。

プロジェクトの外部依存（DB、外部API、メール送信、AI、CDN 等）を特定し、それぞれについて以下を確認:

| 確認ポイント | 内容 |
|---|---|
| 障害パターン | タイムアウト、接続エラー、レート制限、不正レスポンス |
| エラー伝播 | 外部依存の障害が主処理に波及しないか |
| リトライ | タイムアウト・リトライが適切に設定されているか |
| グレースフルデグラデーション | 一部機能の障害で全体が止まらない設計か |

- [ ] 変更がどの外部依存を使っているか特定
- [ ] 各依存先の障害時にどうなるか確認
- [ ] タイムアウト・リトライが適切に設定されているか
- [ ] グレースフルデグラデーション: 一部機能の障害で全体が止まらない設計か

### Step O2: 冪等性・競合状態

時間軸上の安全性を確認する。

- [ ] **二重送信**: 同じリクエストが2回来ても安全か
- [ ] **同時操作**: 複数ユーザーが同時に操作しても整合性が保たれるか
- [ ] **Webhook 再送**: Webhook が再送された場合に二重処理されないか
- [ ] **レースコンディション**: 読み取り → 判定 → 書き込みのパターンで、間に別リクエストが入る可能性はないか
- [ ] **冪等キー**: 冪等性が必要な操作に識別キー（transactionId等）があるか

### Step O3: 可観測性

本番で問題が発生した場合に気づけるか確認する。

- [ ] **エラー監視**: エラーが監視ツール（Sentry等）に報告されるか（try-catch で握りつぶしていないか）
- [ ] **ログ**: 重要な操作にログが出力されているか
- [ ] **エラーメッセージ**: エラーレスポンスに原因特定に必要な情報が含まれているか（ただしPIIは除く）
- [ ] **メトリクス**: レスポンスタイム・エラー率の変化を検知できるか

### Step O4: データプライバシー・PII

個人情報の取り扱いが適切か確認する。

- [ ] **ログ出力**: ログにメールアドレス・氏名・電話番号等のPIIが含まれていないか
- [ ] **APIレスポンス**: レスポンスに不要な個人情報が含まれていないか（必要最小限のフィールドのみ）
- [ ] **エラーメッセージ**: エラー時にDB内部ID・テーブル名・カラム名が露出していないか
- [ ] **URL**: URLパラメータにPII（メールアドレス等）が含まれていないか

### Step O5: ロールバック可能性

デプロイ後に問題が見つかった場合に戻せるか確認する。

- [ ] **コードのロールバック**: 前のバージョンに戻して問題が解消するか
- [ ] **DBマイグレーション**: マイグレーションのロールバック手順が必要か
- [ ] **データ変更の可逆性**: バックフィルスクリプトでデータを変更した場合、元に戻せるか
- [ ] **2段階デプロイの必要性**: コードロールバック時にDB不整合が起きないか（Expand-Contract の確認）

### Step O6: コスト影響

ランニングコストに影響する変更がないか確認する。

- [ ] **DB クエリ数**: 新しい API の1リクエストあたりのクエリ数は妥当か
- [ ] **サーバー実行時間**: 重い処理が追加されていないか
- [ ] **外部 API コール数**: 外部サービスの呼び出し頻度は妥当か
- [ ] **バンドルサイズ**: 新しい npm パッケージが追加されている場合、サイズ影響は

### Step O7: 越境チェック（→ code, → test）

運用観点から隣接領域に踏み込んで確認する。

- [ ] **→ code**: 障害時のエラーハンドリングが実装されているか（try-catch、フォールバック）
- [ ] **→ test**: 障害シナリオ（タイムアウト、外部API失敗）のテストがあるか

## 出力フォーマット

```
=== 運用・耐障害性レビュー結果 ===

[O1: 障害モード] リスクなし / リスクあり
  （リスクありの場合: 障害シナリオと影響・対策）

[O2: 冪等性・競合] 問題なし / 要対応
  （要対応の場合: 競合シナリオと対策案）

[O3: 可観測性] 十分 / 不足
  （不足の場合: 追加すべきログ・監視の指摘）

[O4: データプライバシー] 問題なし / PII露出あり
  （露出ありの場合: 箇所と対策）

[O5: ロールバック] 可能 / 要検討
  （要検討の場合: ロールバック手順の提案）

[O6: コスト影響] 軽微 / 要注意
  （要注意の場合: コスト増加の見積もり）

[O7: 越境チェック]
  → code: OK / 指摘あり
  → test: OK / 指摘あり

総合判定: 運用OK / 要対応 / ユーザー確認必要
  （指摘事項のサマリ）
```

---

## Return Contract

### 返すもの
- 出力フォーマットに従った判定結果（各Step の OK/リスクあり + 指摘事項サマリ）
- 総合判定（運用OK / 要対応 / ユーザー確認必要）

### 返さないもの
- コード調査の途中経過
- grep / git diff の生出力
- 各チェック項目の詳細な調査ログ（結果のみ報告）
