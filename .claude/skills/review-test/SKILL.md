# テスト品質レビュー（/review-test）

## 実行方式

このスキルは **Agent ツールで隔離実行する**。
`/review` オーケストレーターから呼ばれる場合も、単体で呼ばれる場合も同様。

1. Agent ツールを起動し、このスキルの全手順（Step T1〜T6）を渡す
2. Agent はスキルの手順を実行し、Return Contract に従って結果を返す
3. メインコンテキストには判定結果と指摘サマリのみが残る

## 目的

変更内容の品質保証が十分かを検証する。
テストの**存在・網羅性・品質**にフォーカスする。

## 前提

- `git diff` でベースブランチからの変更内容を把握してから開始する
- テスト実行コマンド（CLAUDE.md の TEST_COMMAND）で全テストが通ることを確認してから開始

## 手順

以下のステップを**順番に**実行し、各ステップの結果を報告する。

### Step T0: PJ固有チェックの読み込み

このスキルと同階層の `references/` 配下にPJ固有のチェックファイルがあれば読み込む。
以降のステップに加えて、PJ固有チェックも実行する。

> ファイルがなければこのステップはスキップ。

### Step T1: テスト追加漏れチェック

新規・変更コードにテストが追加されているか確認する。

```bash
# 変更された本体コードのファイル一覧（プロジェクトのソースディレクトリに合わせて調整）
git diff HEAD~1...HEAD --name-only -- 'src/' 'app/' 'lib/' 'components/'

# 変更・追加されたテストファイル一覧（テストディレクトリに合わせて調整）
git diff HEAD~1...HEAD --name-only -- '__tests__/' 'tests/' 'test/' 'src/**/*.test.*' 'src/**/*.spec.*'
```

- [ ] 新規 API ルートにテストがあるか
- [ ] 新規ビジネスロジックにテストがあるか
- [ ] 変更されたロジックのテストが更新されているか
- [ ] テストファイルがプロジェクトの配置規約に従っているか

**テスト不要の変更（指摘しない）:**
- UI のみのスタイリング変更
- 設定ファイルの変更（`.claude/`, `docs/`, `.github/`）
- 型定義のみの変更

### Step T2: テストケース網羅性

テストが十分なケースをカバーしているか確認する。

各テスト対象について以下の観点を確認:

| 観点 | チェック |
|---|---|
| **正常系** | 代表的な入力で期待通りの出力が返るか |
| **異常系** | 不正入力・未認証・権限不足・存在しないIDでエラーが返るか |
| **境界値** | 0件、1件、上限値、空文字、null、undefined |
| **状態遷移** | 各ステータスからの操作可否 |
| **不変条件違反** | CLAUDE.md に不変条件が定義されている場合、違反ケースがテストされているか |

- [ ] 正常系テストがあるか
- [ ] 異常系テストがあるか（最低: 認証エラー、バリデーションエラー、404）
- [ ] 境界値テストがあるか
- [ ] 変更対象に関わる不変条件の違反テストがあるか（定義がある場合）

### Step T3: テスト品質

テスト自体の品質を検証する。

- [ ] **意味のあるアサーション**: `expect(result).toBeDefined()` のような弱いアサーションではなく、具体的な値を検証しているか
- [ ] **テスト名**: テスト名が「何をテストしているか」を明確に表現しているか
- [ ] **独立性**: テスト間に依存関係がないか（実行順序に依存しない）
- [ ] **実装詳細への非依存**: 内部実装ではなく、入出力（振る舞い）をテストしているか
- [ ] **テストデータ**: ヘルパー/ファクトリを活用しているか、ハードコードされた長いデータが散在していないか

### Step T4: モック品質

モックが実際の振る舞いを正確に反映しているか確認する。

- [ ] **モックパターン**: プロジェクトで定義されたモックパターンに準拠しているか
- [ ] **モックの正確性**: モックの戻り値が実際のDB/APIの型・構造と一致しているか
- [ ] **過剰モック**: 実際にモックが必要なもの以外をモックしていないか（テストの信頼性低下）
- [ ] **外部依存のモック**: DB、外部API、ファイルシステム等の外部依存が適切にモックされているか

### Step T5: テスト実行結果

テストが実際に通るか確認する。

```bash
# プロジェクトのテストコマンドを実行（CLAUDE.md 参照）
# 例: npx vitest run / npx jest / npm test
```

- [ ] 全テストが PASS するか
- [ ] 新しい warning / deprecation が出ていないか
- [ ] テスト実行時間が著しく増加していないか

### Step T6: 越境チェック（→ code, → ops）

テスト観点から隣接領域に踏み込んで確認する。

- [ ] **→ code**: モックが実装の実態を正確に反映しているか。実装で使われている分岐条件がテストでカバーされているか
- [ ] **→ ops**: 障害シナリオ（タイムアウト、外部API失敗）のテストがあるか

## 出力フォーマット

```
=== テスト品質レビュー結果 ===

[T1: テスト追加] OK / 漏れあり
  （漏れありの場合: テストが必要なファイル・関数の指摘）

[T2: ケース網羅性] OK / 不足あり
  正常系: OK / 不足
  異常系: OK / 不足
  境界値: OK / 不足
  不変条件違反: OK / 不足 / 対象外
  （不足の場合: 追加すべきテストケースの具体例）

[T3: テスト品質] OK / 要改善
  （要改善の場合: 改善箇所の指摘）

[T4: モック品質] OK / 要改善
  （要改善の場合: モックの問題点）

[T5: テスト実行] 全PASS / FAIL あり
  （FAIL の場合: 失敗テスト名とエラー内容）

[T6: 越境チェック]
  → code: OK / 指摘あり
  → ops: OK / 指摘あり

総合判定: テストOK / テスト追加必要 / テスト修正必要
  （指摘事項のサマリ）
```

---

## Return Contract

### 返すもの
- 出力フォーマットに従った判定結果（各Step の OK/NG + 指摘事項サマリ）
- 総合判定（テストOK / テスト追加必要 / テスト修正必要）

### 返さないもの
- テスト実行の全出力ログ
- grep / git diff の生出力
- テストファイルの内容全文（問題箇所の引用のみ）
