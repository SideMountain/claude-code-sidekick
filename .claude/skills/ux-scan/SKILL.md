# /ux-scan — UX 導線フリクションのプロファイラ

コードベースの静的トレースで「機能への到達コスト」を計測し、頻度加重スコアで導線フリクションを順位付けする。実ユーザー・実行環境なしで回る（動的モードは任意拡張）。
計測ルーブリック・型カタログ・報告フォーマットの正は `references/ux-scan-kit.md` — **最初に必ず Read する**。ルーブリックは PJ 導入時に凍結し、before/after 比較の物差しを固定する。

分類: 対話型（パターン D・部分委譲）。初回のタスクリスト合意は人間ゲート、導線トレースは Agent 委譲可。

## Step 0: モード判定

- `docs/ux-tasks.md` が**ない** → 初回導入（Step 1〜3）
- **ある** → 再スキャン（Step 4 へ。before/after 差分を出す）

## Step 1: 現状調査（初回のみ）

1. ルート定義・ナビゲーション定義（メニュー・タブの constants）・主要画面を列挙する
2. 想定ユーザーのロールを列挙する（仕様・README・認可コードから読み取り、読み取れなければ質問）

## Step 2: タスクリスト起案 → 人間合意（初回のみ・飛ばさない）

1. 業務の目的単位で候補タスク 15〜20 件を**動詞形**で列挙し、頻度の推定値と理論最短手数の案を添えて提示する
2. **ここで停止し、人間が Top10 と頻度・理論最短を確定するまでスキャンに進まない**（頻度と理論最短は人間確定値。以後スキャナは書き換えない）
3. 確定値で `docs/ux-tasks.md` をキット §3 のテンプレで作成する

## Step 3: 静的スキャン

キット §4.1 の手順で実行する。トレース作業は Agent 委譲してよい（下記 Return Contract）:

1. タスクごとに経路表を作る（入口 → 画面 → タップ対象 → 遷移 → 完了。**各ステップに file:line**）
2. キット §2.2 の計数規約で 手数・分岐数・遠回り度 を算出する
3. F1〜F8（キット §2.6）で横断検査する（F2・F7・F8 は grep が効く）
4. 種別タグ（意図的 / 副作用 / 未整備）を ADR・コードコメント・git 履歴から判定し、出典を引用する
5. **処遇 3 択**（キット §2.5: 磨く / 消す / 機械向け口に落とす）をスコア上位に付ける。「消す」「機械向け口」は根拠（裁量の有無・実際の消費者が誰か）を 1 行添える
6. キット §6 のフォーマットで報告し、`docs/ux-scans/YYYY-MM-DD.md` に保存、`docs/ux-tasks.md` の実測列を更新する

制約:

- 診断のみ。修正の実装はしない（提案まで）
- スコアの根拠には必ず file:line か操作ログを引用する
- 確信の持てない頻度・種別・処遇は「要人間確認」と明示し、推測で埋めない（曖昧なまま欠陥と断定しない）

## Step 4: 再スキャン（2 回目以降）

1. `docs/ux-tasks.md` の全タスクを同一ルーブリックで再計測する
2. キット §5 の差分判定を出す: スコア増 = **回帰**として報告の先頭に置く。意図的回帰は ADR 参照付きで明示する
3. 総コストの推移を 1 行で示す

## 動的モード（任意・環境がある場合のみ）

dev / プレビュー環境と専用テストユーザーが用意できる場合のみ、キット §4.2 に従いブラウザエージェントで実操作計測し、静的モードの手数と突合する（一致率がルーブリックの校正材料になる）。本番資格情報は使わない。

## Return Contract（トレースを Agent 委譲する場合）

### 返すもの

- タスクごとの経路表（ステップ列 + file:line）と 手数・分岐数の計数
- F1〜F8 該当の検出リスト（型番号 + 根拠 file:line + 1 行説明)
- 判定不能だった箇所のリスト（「要人間確認」明示）

### 返さないもの

- 読んだファイルの全文・探索の試行錯誤ログ
- ルーブリックの解釈変更の提案（ルーブリックは凍結済み。変更提案はメインで人間に出す）

### 出力フォーマット

キット §6 の順位表の行データ（スコア計算はメイン側で頻度重みを掛けて確定する）。
