# UX 導線スキャンキット — 計測ルーブリックと手順

> 読者: 下流プロジェクトの Claude（runtime）· 役割: 仕様（`/ux-scan` の計測規約）· ロード条件: `/ux-scan` 実行時に Read（常駐しない）。

## §1 思想 — プロファイラ = コスト会計

「良い UX スコア」は作らない。良さの合成は主観の合成になり、再実行しても同じ値が出ない。代わりにパフォーマンスプロファイラと同じ会計をやる: **タスク頻度 × 到達コスト**を計上し、理論最短との差 = **遠回り度**を出す。hot path（毎日の操作）が深ければ欠陥、cold path（月 1 の設定画面）が深いのは正常。

- 系譜: KLM（Card & Moran, 1980）/ GOMS（Card, Moran & Newell, 1983）— 操作列から所要時間を予測する古典手法の簡略版（タップ＋画面遷移＋考える分岐）に頻度加重を掛けたもの
- 「3 クリックルール」（3 クリック以内でないと離脱する）は根拠の弱い俗説（NN/g "The 3-Click Rule for Navigation Is False" / Porter, UIE 2003: クリック数と成功率・満足度に相関なし）。**本質はクリック数の絶対値でなく頻度加重** — 毎日の操作が 4〜6 タップなら欠陥、月 1 の操作が 6 タップでも欠陥としない

## §2 ルーブリック（PJ 導入時に確定したら改修サイクル中は変更しない = before/after 比較の前提）

### 2.1 3 秒ルール（運用定義）

高頻度の**単純操作**（テキスト入力そのものが主目的でない操作: 承認・割当・送信・検索・遷移）で、「① 入口を探す ② 辿り着く ③ どれを使うか考える」の合計が **3 秒 / 3 タップを超える**、または**「考える分岐」が 1 回でもある**ならフリクションとして記録する。静的モードではタップ数と分岐数で代理判定する（エージェントの操作時間は人間と一致しないため、時間は参考値・**手数と分岐数が正**）。

### 2.2 スコア式と計数規約

```
スコア = 頻度 ×（タップ ＋ 画面遷移）× 認知負荷
```

- **手数** = タップ（クリック）数 ＋ 画面遷移数。モーダル / ドロワーの開閉は遷移 1、確認ダイアログの OK はタップ 1。1 画面分を超えるスクロールは 1 手（KLM の厳密なオペレータ分解はしない）
- **頻度の既定重み**（導入時にタスクごとに人間が確定。以後凍結）: 毎日複数回 = 50 / 毎日 = 20 / 週数回 = 8 / 週 1 = 4 / 月 1 以下 = 1（cold path。深くても原則欠陥としない）
- **認知負荷** = 考える分岐なし: 1 / あり: 2（分岐の個数は列に別途記録し、根拠説明と回帰検知に使う）
- **遠回り度** = 実測手数 − 理論最短手数。理論最短は「現在の情報設計を白紙にした場合に UI 慣習上可能な最少手数」を人間と合意して記入する

### 2.3 「考える分岐」の判定基準（いずれかで 1 分岐）

1. **どの入口か**: 同じ目的の操作口が複数あり、選ぶ必要がある
2. **どのタブ / カテゴリか**: 対象の分類が予測できず、探す必要がある
3. **どっちのボタンか**: 紛らわしいラベルのペアから選ぶ必要がある
4. **内部概念の理解が前提**: システム内部の状態モデルを知らないと次の操作が決められない

「初見だけ迷い、習熟すると消える」分岐も数える（新任コスト＋認知の常時課税として頻度側で減衰させない）。

### 2.4 種別タグ（3 値）

| タグ | 意味 | 扱い |
|---|---|---|
| **意図的（ADR あり）** | 過去の設計判断に由来。ADR・コードコメントを引用できる | 「前提が変わったか」を必ず検討。変わっていれば値札付きで再交渉 |
| **集約・撤去の副作用** | 別の改善の反動で深くなった | 改善の巻き戻しでなく、浅い入口の再設置を検討 |
| **未整備** | 単に作り込まれていない | 通常のバックログ |

### 2.5 処遇（disposition）3 択 — スコアの帰結

インターフェースは「人間の判断の所在」に張り付く。スコア上位の各導線に、改善の向きを 3 択で付ける:

| 処遇 | 判定基準 | 帰結 |
|---|---|---|
| **磨く** | 裁量・承認・例外処理・複数人の調整がフローの本体 | 導線を浅くする（従来の UX 改善） |
| **消す** | 高頻度 × 裁量ゼロ（毎回同じ判断しかしない） | 自動化して導線自体を無くす。**最速の導線は導線の不在** |
| **機械向け口に落とす** | 実際の消費者が人間でなく別システム / エージェント | UI をやめて API / MCP を第一級の口にする。人間用は薄いビューアに |

### 2.6 フリクション型カタログ（8 種・PJ 非依存）

| # | 型 | 定義 | 検知のヒント |
|---|---|---|---|
| F1 | **内部概念の露出** | システム内部の状態・役割の区別を利用者に強いる | 同一エンティティが状態によって別タブ / 別画面に現れる。ドメイン用語ペアが UI ラベルに露出 |
| F2 | **同一目的の入口の多重化** | 同じ操作の入口が複数系統あり、毎回どれを使うか判断させる | 同じ mutation / API を呼ぶハンドラが複数コンポーネントに存在。専用ルートと埋め込みタブの併存。ナビに載らない孤立ルート |
| F3 | **日常操作が深い** | hot path が 4 タップ以上（一覧→詳細→タブ→モーダル→確認の入れ子） | 高頻度タスクの経路にモーダル入れ子・確認ダイアログ。行アクションがなく詳細経由が必須 |
| F4 | **分類が非直感** | 分類軸が業務単位でなく実装都合。対象がどこに出るか予測できない | カテゴリ数 ≫ タブ数の多対一。「その他」の肥大。カウント表示とタブの粒度不一致 |
| F5 | **一覧から離脱して完結しない** | 「対応する」系の一覧なのに、操作のために別画面へ飛ばされる | 行アクションの実体が詳細ページへのリンク |
| F6 | **プレビューの袋小路** | プレビューが閲覧専用で、操作には結局フル画面を開き直す | プレビュー内に主要アクションのボタンがない。画面幅で挙動が変わる |
| F7 | **同一ドメイン操作の送信口の散在** | 同種の操作（例: 通知送信）が用途別に別 UI・別実装 | 送信系の API 呼び出しを grep すると複数箇所に散在 |
| F8 | **命名・ラベル不一致** | 同一機能に複数の呼称。ナビラベルと URL・実装名の食い違い | 同一機能の呼称が grep で 2 系統以上。ナビ定義とルートスラッグの不一致 |

## §3 タスクリスト — `docs/ux-tasks.md`（PJ 側インスタンス）

```markdown
# UX タスクリスト（UX 回帰テストの入力。ルーブリックは ux-scan スキルの references/ で固定）
<!-- 頻度・理論最短は人間確定値。実測手数・分岐数・遠回り度・処遇はスキャンごとに更新 -->

| ID | タスク | 想定ユーザー | 頻度 | 理論最短 | 実測手数 | 分岐数 | 遠回り度 | 処遇 | 最終計測日 |
|----|--------|--------------|------|----------|----------|--------|----------|------|------------|
| T01 | 申請を承認する | 管理者 | 毎日複数回 | 2 | 5 | 2 | +3 | 磨く | YYYY-MM-DD |
```

- タスクは**動詞で書く**（「〜画面を見る」でなく「〜する」）。UI の現状構造から逆算せず、業務の目的単位で切る
- Top10〜15 件。hot path を網羅し、cold path は代表 2〜3 件でよい。頻度・理論最短は人間確定値 — スキャナが書き換えない
- 導線を変える PR はこのファイルの該当行の更新を伴う（タスクリスト自体が仕様の一部）

## §4 スキャン手順

### 4.1 静的モード（コード導線トレース）— まずこちら。環境不要

1. ルート定義 → ナビゲーション定義（メニュー・タブの constants）→ 対象画面のクリックハンドラ・モーダル起動、の順に骨格を読む
2. タスクごとに経路表を作る: `入口 → 画面 → タップ対象 → 遷移/モーダル → … → 完了`。**各ステップに file:line を添える**
3. F1〜F8 のヒントで横断検査（grep が効くのは F2・F7・F8）
4. §2.2 の規約で計数し `docs/ux-tasks.md` を更新。種別タグは ADR・コードコメント・git 履歴から判定し出典を引用。処遇（§2.5）を提案する

限界: 画面幅依存の挙動（F6）・体感待ち時間・実際に迷うかは読めない。動的モードで補う。

### 4.2 動的モード（ブラウザエージェントによる実操作計測）

- Playwright の**アクセシビリティツリー方式**を主体にする（スクリーンショットの Vision 処理でなく、構造化テキストで要素 ref 指定の決定論的操作。コーディングエージェント用途では MCP より CLI + Skills 構成がトークン効率で有利 — 出典: https://github.com/microsoft/playwright-mcp / https://playwright.dev/docs/getting-started-mcp ）
- 計測は**エージェントの操作ログからタップ数・遷移数・引き返し回数**を数える（これが正。所要時間は参考値）
- セキュリティ: 対象は開発 / プレビュー環境限定・専用テストユーザー・本番資格情報を持たせない。任意コード実行系ツールは使わない

## §5 再実行 = UX の回帰テスト

- 改修後に**同一タスクリスト × 同一ルーブリック**で再スキャン。ルーブリックを変えたくなったら「次のベースライン取り直し」として別サイクルにする
- 結果は `docs/ux-scans/YYYY-MM-DD.md` に保存し、`docs/ux-tasks.md` の実測列を更新する
- **差分判定**: スコア減 = 改善 / 同値 = 不変 / 増 = **回帰**。回帰が 1 件でもあれば報告の先頭に出す（テストの赤と同じ扱い）。意図的トレードオフによる回帰は ADR 参照を添えて「意図的回帰」として記録する — 黙って許容しない
- 合計スコアの推移を 1 行で示す（例: 総コスト 612 → 388、−37%）

## §6 報告フォーマット

1. **ルーブリック掲示**: 3 秒ルールとスコア式を冒頭に再掲（毎回同じ物差しであることの宣言）
2. **順位表**（スコア降順）: `順位 / 導線（症状 1 行）/ 型 / 頻度 / 手数 / 認知負荷 / 種別 / 処遇 / スコア`
3. **特に効く 3 個**: 対象順位 → 提案 1 文 → なぜ効くか（頻度 × 削れる手数）。複数フリクションを一手で潰せる提案を優先
4. **根拠**: 項目ごとに 現状経路 → 過去の意図（ADR・コメント引用）→ 前提の変化 → 修正方向。**必ず file:line を引用**
5. **進め方**: おすすめ 1 件＋選択肢 2 件程度。実装まで踏み込まない（診断と設計の分離）
