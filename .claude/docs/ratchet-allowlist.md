# allowlist + ratchet — 既存違反が多い規範を段階導入する型

> 遅延ロード doc（常駐しない）。新しい規範（UI 安全・エラーハンドリング・命名等）を
> 「既存コードに違反が N 件ある状態」から強制したいときに Read する。

## 問題

新しい規範を作った時点で、既存コードには大量の違反が残っている。選択肢が両極端になりがち:

- **全是正してから強制** → 是正が大きすぎて規範自体が塩漬けになる
- **強制せず認知層のみ** → ルールは存在するのに違反が増え続ける（ルールだけでは行動は変わらない）

## 型（3 点セット）

1. **検知スクリプト**: 違反面を機械で列挙する（grep / AST。決定的であること）。
2. **allowlist（理由付き）**: 既存違反を 1 行 1 件で列挙したファイル。**なぜ未対応かの理由をコメントで併記**する。
   これは「免除リスト」ではなく**可視化された負債台帳** — 消し込みが進捗になる。
3. **ratchet（上限値）**: `MAX_UNGUARDED=<現在の違反数>` を検知スクリプトに持たせ、
   **カウントが上限を超えたら commit をブロック**する（pre-commit 配線）。
   - 新規コードは規範に従うか、理由付きで allowlist に追加して上限を明示更新するかの二択になる
   - 既存違反を是正したら上限を**下げる**（ratchet = 逆戻りしない爪車）

## 配線

- pre-commit（`.claude/githooks/`）に検知スクリプトを配線する。対象ファイルを含むコミットのみ実行し、
  無関係なコミットを遅くしない（path フィルタ）
- 検知スクリプト自体の偽陰性を実データで検証してから配線する（検出パターンが実在の違反 variant を
  拾えないと「回しても緑」の偽安心になる）

## 運用

- allowlist の追加は「理由を書く」摩擦を意図的に残す（安易な免除の抑止）
- 消し込みは通常の改修 PR に同乗させる（触ったファイルの violation はそのついでに直す）
- 上限が 0 になったら allowlist と ratchet を撤去し、検知スクリプトだけ残す（恒久ゲート化）

## この型を選ばないケース

- 違反が少数（数件）→ 先に全是正して最初から強制する方が速い
- 決定的に検知できない規範（設計判断を要する）→ レビュー観点（REVIEW.md）に置く。機械ゲートにしない
