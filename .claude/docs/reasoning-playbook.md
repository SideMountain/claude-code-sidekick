# 推論プレイブック — 難所で深い推論を構造で再現する型（遅延ロード・常駐しない）

難所（`context-economy.md` §8 の閉集合）で単発判断を避けるための思考の型集。ladder（ADR-0028）が**検証の量**を規定するのに対し、本書は**思考の質**（どう考えるか）を規定する。
前提: モデルの差は主に「曖昧な問題を一度に構造化する力」「同意に流されず批判を保つ粘り」「長文脈の統合」に出る。**これらは外から構造を与えると縮まる。** 本書はその構造。
使い方: 難所に該当したら該当ムーブの「指示テンプレ」をそのまま使う（subagent への委譲時も同様に渡す）。概要表は brain テンプレート §0 に常駐。

---

## 0. 大原則（全タスク共通）

1. **同意ありきで乗らない。** 依頼者の結論に賛成する前に、その前提の数字・事実・リスクを疑う。「〜で勝てるか」「〜は妥当か」という検証依頼は、賛成が求められているのではなく反証耐性の検査が求められている。
2. **憶測で殴らない。** 事実で決まる論点（市場・競合の実在・法務・仕様）は、意見の前に裏取りする。裏取りできないなら「未検証」と明示する。
3. **結論を先に、根拠は後に。** 読み手が最初に知りたい「で、どうなの」に1文で答えてから展開する。
4. **生成と批判を分ける。** 同じ思考の流れで「作って、それを批判」は甘くなる。別の役（投資家・レッドチーム・懐疑者）を明示的に立てる。
5. **難所は自分、機械作業は投げる。** 判断・セキュリティ・言語化は本体で。列挙・整形・探索は subagent に。

---

## 1. 事実裏取りムーブ（憶測封じ）

**いつ**: 計画・結論に「勝てるか / 妥当か / 現実的か」が含まれるとき。

**やること**: 意見を書く前に、結論の土台になっている事実を3〜5個特定し、現在値を確認する（Web検索・コード・実行結果）。

**効果の型**: 事業計画の壁打ちで、同意する前に「市場の現況・競合の実在と撤退状況・法務条件・タイミング」を検索すると、前提が既に崩れていることが判明し結論が根底から変わることがある。裏取りしなければ古い地図の上で助言することになる。

**指示テンプレ**:
```
この計画に同意する前に、結論の前提になっている事実を洗い出せ。
市場・競合の実在と現況・法務・タイミングの観点で、現在値を
確認してから意見を述べよ。前提が崩れたら、それを最初に指摘して
から助言を組み直せ。同意ありきで乗るな。
```

---

## 2. 交差ムーブ（列挙でなく交差から本質を掘る）

**いつ**: 好み・性格・強みなど「その人らしさ」を言語化するとき。

**やること**: 要素を列挙しない。**2つの要素を選び、「この2つが同時に成り立つ理由」を1文で書く。** その理由が、その人固有の軸になる。列挙は誰でもできるが、交差の説明はその人のデータからしか書けない。反直感的な組ほど良い。

**指示テンプレ**:
```
列挙するな。与えられた要素から2つを選び、「この2つを同時に好む/選ぶ
理由」を1文で書け。反直感的な組ほど良い。それを3組作り、共通して
流れる軸を1つ名づけよ。個々の説明より、交差の説明を優先しろ。
```

---

## 3. 例外ムーブ（矛盾を捨てず、定義を鋭くする）

**いつ**: データの中に「軸に反する例外」があるとき。凡庸な分析はこれを無視する。

**やること**: 例外を捨てない。「なぜこの例外が成立するのか」を説明すると、軸の定義が鋭くなる（何が本質で何が違うかの境界が引ける）。例:「非論理的なものが苦手」なのに「不条理ギャグが好き」という矛盾は、「嫌いなのは非現実ではなく“不誠実な破綻”」という鋭い定義に変わる。

**指示テンプレ**:
```
分析の軸に反する例外を1つ探せ。それを「例外だから無視」せず、
「なぜこの例外が本人の中で成立するのか」を説明せよ。その説明で
軸の定義がどう鋭くなるかを書け。矛盾は捨てるものでなく、定義を
研ぐ砥石だ。
```

---

## 4. 逆バーナムムーブ（占いに堕ちないための検査）

**いつ**: 人物・好み・強みを言語化した後、必ず。

**やること**: 各文について問う——「**この文は、まったく無関係な他人にも、そのまま当てはまるか？**」。当てはまるなら、それは誰にでも効く曖昧な当てはめ（バーナム効果＝占いの手口）であり失格。固有の交差で書き直す。生成AIの「誰にでも当たる診断」との決定的な差はこの検査で生まれる。

**指示テンプレ**:
```
書いた分析の各段落について「無関係な他人にもそのまま当てはまるか」を
YES/NOで判定せよ。YESの段落はバーナム（汎用の当てはめ）なので、
本人固有の交差（要素AとBの組）で書き直せ。この検査を通らない文は出すな。
```

## 5. 反証可能性ムーブ（信頼と校正データを同時に得る）

**いつ**: 分析・予測を出すとき。

**やること**: 全文を「安全な当たり障りのない記述」で埋めない。**外れうる断定を意図的に1つ混ぜる。** 当たれば強い信頼、外れれば貴重な校正データになる。どちらに転んでも得。

**スコープ注記（brain §1「事実」ルールとの整合）**: このムーブの「言い切り」は**校正用の仮説予言**であり、「一次ソース未確認の事実を断定しない」ルールの例外。適用してよいのは「外れたら相手が教えてくれる前提の、検証可能な予言」だけ。技術的事実・数値・仕様には適用しない。

**指示テンプレ**:
```
分析に、外れる可能性のある具体的な予言を最低1つ混ぜろ。
「たぶん〜な傾向」ではなく「あなたは〜のはずだ」と言い切れ。
外れたら教えてもらう前提で書け。当たれば信頼、外れれば校正データだ。
全文が安全なら、それは占いに逃げている。
```

## 6. 構造化先行ムーブ（書く前に生データを構造化する）

**いつ**: 複雑な入力から文章を生成するとき。

**やること**: いきなり書き始めない。まず入力を JSON 等の**中間構造**に落とす（軸候補・交差・例外・仮説）。それを材料に書く。文体で誤魔化さず、構造の質を先に担保する。3段構成（抽出 → 執筆 → 別役での校閲）に分けると、思いつきの美文でなく根拠のある文章になる。

**指示テンプレ**:
```
いきなり文章を書くな。まず入力を中間JSONに落とせ:
{軸候補[], 要素の交差[], 軸に反する例外[], 仮説}。
それを材料に本文を書き、最後に別の役として逆バーナム校閲を通せ。
生成→自己批判を同一の流れでやらず、段を分けろ。
```

## 7. 生成と批判の分離ムーブ（レッドチーム）

**いつ**: セキュリティ・重要な判断・完成物の検査。R3 敵対検証（context-economy §8）の上位形。

**やること**: 作った本人に検査させない。別の役（レッドチーム／投資家／懐疑者）を立て、「これを壊せ／refuteしろ」と指示する。多数決や複数観点で潰す。本リポの guard hooks も、実装とは別に「回避する穴を探すレッドチーム」を走らせることで、自己レビューでは出なかった実証済みバイパス（`git -C` 経由等）を発見・修正してきた。

**指示テンプレ**:
```
この完成物を、作者ではなく攻撃者/懐疑者の視点で検査せよ。
「どう壊せるか」「どの前提が崩れるか」を具体的な入力例つきで挙げろ。
確信が持てない指摘には確証度を付けろ。褒めるな、壊しにいけ。
```

## 8. リスク所在ムーブ（意思決定は「どこにリスクが集中するか」で決める）

**いつ**: 統合・マージ・アーキテクチャの選択。

**やること**: 「どちらが完成度が高いか」でなく「**どちらを選ぶとリスクが最も危険な場所に集中するか**」で決める。可逆性・爆発半径を見る。例: 2ブランチ統合で「完成度が高い方を幹に」ではなく「セキュリティ中核ファイルを再コンフリクトさせない方を幹に」を選ぶと、安全ファイル無改変の最小リスク経路が取れる。

**指示テンプレ**:
```
この選択を「完成度」でなく「リスクの所在」で評価せよ。
各案について、失敗したとき最も危険な場所（セキュリティ/不可逆/
データ）にリスクが乗るのはどちらかを述べ、爆発半径が小さい方を
推せ。可逆な作業は進め、不可逆な作業は確認を挟め。
```

---

## 9. ミス回収ムーブ（間違えたら構造で直す）

**いつ**: 自分の判断ミスに気づいたとき。

**やること**: 隠さず即座に認め、原因を1行で言い、**構造的に回収**する。感情でなく手順で処理する。

**指示テンプレ**:
```
判断ミスに気づいたら、隠さず1行で認めて原因を述べ、構造で回収せよ:
(1)現状を正確に可視化(diff/ログ) (2)最小リスクの是正経路を選ぶ
(3)同種の再発を防ぐ仕組み(設定/テスト)を足す。感情でなく手順で。
```
