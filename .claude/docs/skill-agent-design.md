# Skills と Agents の設計ガイドライン

Claude Code の実行アーキテクチャは3層で構成される。
このガイドラインは、スキルやエージェントを新規作成・改修する際の判断基準を定義する。

---

## 1. 3層モデル

```
Commands（ユーザー入力）
  → Agents（実行主体。隔離されたコンテキスト・ツール権限・モデル選択）
    → Skills（再利用可能な知識・手順）
```

| 層 | 何か | 置き場 | 例 |
|---|---|---|---|
| Commands | ユーザーが呼ぶエントリーポイント | `/skill-name` | `/review`, `/inventory` |
| Agents | 実行主体。独自のコンテキスト・権限を持つ | `.claude/agents/` or Agent ツール | reviewer, researcher |
| Skills | 「何をするか」の知識・手順 | `.claude/skills/` | review-code, scoring-guide |

### 各層の責務

- **Commands**: ユーザーとの接点。何を呼ぶかだけを決める
- **Agents**: 「誰がやるか」。メインコンテキストとは隔離された独自コンテキストで動く
- **Skills**: 「何をするか」「何を知っているか」。エージェントに渡される手順、またはメインで直接実行される手順

---

## 2. スキルの分類

スキルは用途で3つに分類される。

| 分類 | 性質 | コンテキスト隔離 | 例 |
|---|---|---|---|
| **タスク型** | 調べて→まとめて→報告。途中でユーザー判断が不要 | する | `/news`, `/inventory`, `/review-code` |
| **対話型** | 途中でユーザーの確認・承認・判断が必要 | しない | `/close-chat`, `/setup`, `/record-decision` |
| **参照型** | 手順ではなく知識。スキルから読み込まれるリソース | — | `scoring-guide`, `feedback-compression-rules` |

> **Note**: 参照型は SKILL.md ではなく `references/` に配置されるリソース。
> スキルの分類に含めているのは、設計時に「この知識はどこに置くか」を判断するため。

### 判断フロー

```
新しいスキルを作る
  │
  ├── 途中でユーザーに聞く必要があるか？
  │     → Yes → 対話型（メインで直接実行）
  │     → No  → タスク型（Agent ツールで隔離実行。サマリだけメインに返す）
  │
  └── そもそも手順ではなく知識か？
        → Yes → 参照型（references/ に配置。スキル本文から明示的に読み込む）
```

## 3. コンテキスト隔離の設計

### なぜ隔離するか

スキルの中間過程（API呼び出し、調査ログ、照合結果）がメインコンテキストに蓄積すると、
同一セッション内の後続作業の推論精度が落ちる。
隔離することで、メインには結果サマリだけが返り、コンテキストがクリーンに保たれる。

### 実装方法: Agent ツールによる委譲

タスク型スキルは、スキル本文の冒頭で Agent ツールへの委譲を指示する。

```markdown
## 実行方式

このスキルは Agent ツールで隔離実行する。
メインコンテキストを保護するため、以下の手順で実行すること:

1. Agent ツールを起動し、このスキルの全手順を渡す
2. Agent はスキルの手順を実行し、Return Contract に従って結果を返す
3. メインコンテキストには結果サマリのみが残る
```

> **将来の移行パス**: Claude Code の `context: fork` フロントマターが安定したら
> （現時点では不安定: [#18394](https://github.com/anthropics/claude-code/issues/18394)）、
> frontmatter ベースの宣言的な隔離に移行する。
> その際、スキル本文の「実行方式」セクションは不要になり、
> frontmatter に `context: fork` を追加するだけで済む。
> Return Contract はそのまま活用できる。

### サマリ設計（Return Contract）

**隔離実行するスキルには必ず Return Contract を定義する。**
サブエージェントに「何を返すか」を明示しないと、中間ログが全部返るか、必要な情報が落ちる。

対話型スキル（メインで直接実行するもの）には Return Contract は不要。
メインコンテキストで実行されるため、出力の制御はスキル本文の「出力フォーマット」で十分。

スキル本文の末尾に以下のセクションを設ける:

```markdown
## Return Contract

### 返すもの
- （メインコンテキストに必要な情報を列挙）

### 返さないもの
- （中間過程で不要な情報を列挙）

### 出力フォーマット
（サマリの形式を定義）
```

**設計のコツ:**
- 「返すもの」はユーザーが判断・行動するために必要な情報だけに絞る
- 「返さないもの」は中間過程（API呼び出しログ、照合の途中経過、取得した生データ等）
- 出力フォーマットは既存の「出力フォーマット」セクションをそのまま活用する

## 4. `.claude/agents/` の設計（応用）

### 現状と方針

現時点では `.claude/agents/` にカスタムエージェント定義を作成しない。
Agent ツールによる委譲で十分に隔離が実現でき、管理対象を増やす必要がないため。

### いつカスタムエージェント定義を作るか

以下のいずれかに該当する場合に検討する:

| 要件 | Agent ツールで十分 | カスタム定義が必要 |
|---|---|---|
| 単にコンテキストを隔離したい | Agent ツールで委譲 | — |
| ツール権限を制限したい | — | カスタムエージェントで `tools:` を指定 |
| 特定の知識を事前注入したい | — | カスタムエージェントで `skills:` を指定 |
| モデルを固定したい（コスト最適化等） | — | カスタムエージェントで `model:` を指定 |
| 同じ設定で複数スキルから呼ばれる | — | 共通のカスタムエージェントを定義 |

### エージェント定義の書き方（参考・将来用）

> **注意**: 以下のフォーマットは公式ドキュメントに記載されているが、
> `agent:` フィールドや `skills:` の動作は現時点では不安定（§7 参照）。
> `context: fork` が安定した時点で検証の上、採用する。

```markdown
# .claude/agents/reviewer/AGENT.md
---
name: reviewer
description: "コードレビューの専門家。変更を分析し判定を返す。"
model: sonnet
tools: Read, Grep, Glob, Bash
skills:
  - scoring-guide
---

あなたはコードレビューの専門家です。
preloaded されたスキルに従い、変更を分析して判定を返してください。
```

### 注意事項

- エージェントは「多く作りすぎない」。明確な専門性の違いがある場合にのみ分ける
- エージェントの責務が曖昧なら、まだ作る時期ではない
- 各PJで必要になったエージェントは、汎用的であればベースリポジトリに還元する

## 5. 組み合わせパターン

### パターンA: タスク型スキル + Agent 委譲（基本）

スキル本文に「Agent ツールで隔離実行」の指示と Return Contract を記述する。
最もシンプル。Agent が手順を実行し、サマリだけメインに返る。

例: `/news`, `/inventory`, `/review-code`

### パターンB: オーケストレーター + 子スキル委譲

親スキルがメインで実行され、複数の子スキルを Agent ツールで並列実行する。
各子スキルの結果を統合して最終判定を出す。

例: `/review`（→ `/review-code`, `/review-test`, `/review-ops` を並列実行）

### パターンC: 対話型スキル（隔離しない）

途中でユーザー判断が必要なスキル。メインコンテキストで直接実行する。

例: `/close-chat`, `/setup`, `/record-decision`

### パターンD: 対話型 + 部分委譲（ハイブリッド）

対話型スキルの中に重い調査フェーズがある場合、調査部分だけ Agent に委譲し、
対話部分はメインで実行する。

例: `/weekly-inventory`（Step 1-5 の分析を Agent に委譲 → Step 6 の承認はメインで対話）

> 実装の参考: `.claude/skills/weekly-inventory/SKILL.md` を参照。
> 委譲部分には Return Contract が必要。対話部分はメインの出力フォーマットで制御する。

## 6. 設計チェックリスト

新しいスキルを作るとき、以下を確認する:

- [ ] **分類**: タスク型 / 対話型 / 参照型 のどれか
- [ ] **隔離判断**: 途中でユーザー判断が必要か → Yes: メイン実行 / No: Agent 委譲
- [ ] **Return Contract**: 隔離する場合、返すもの・返さないもの・出力フォーマットを定義したか
- [ ] **参照資料**: 事前に読むべき知識があるか → あれば references/ に配置し、スキル本文で読み込み指示

## 7. 既知の制約と将来の移行パス

### 現時点の制約（2026-04 時点）

| 機能 | 状態 | 参照 |
|---|---|---|
| `context: fork` | 公式ドキュメントに記載あるが不安定（成功率~5%） | [#18394](https://github.com/anthropics/claude-code/issues/18394) |
| `agent:` フィールド | Skill ツール経由で無視される | [#17283](https://github.com/anthropics/claude-code/issues/17283) |
| `allowed-tools` | 制御が効かない | [#18837](https://github.com/anthropics/claude-code/issues/18837) |
| VSCode バリデータ | 基本フィールドのみ認識 | [#25380](https://github.com/anthropics/claude-code/issues/25380) |

### 移行計画

`context: fork` が安定したら:

1. 各タスク型スキルの frontmatter に `context: fork` を追加
2. 「実行方式」セクションを削除（frontmatter が自動で隔離する）
3. Return Contract はそのまま維持（サマリ設計は隔離手段に依存しない）
4. 必要に応じて `.claude/agents/` にカスタムエージェント定義を作成し、`agent:` フィールドで指定
