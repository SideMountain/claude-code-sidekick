# 知識還流の判定リファレンス（単一ソース）

feedback → brain → OSS テンプレートの**昇格ラダー**を判定する rubric と few-shot の唯一の正。`/close-chat`（Step 2.5）・`/weekly-inventory`（Step 0a/3b/3c/4）・`/auto-implement`（Phase 5b）・`rules/knowledge-map.md` はこの 1 ファイルを参照する（4 箇所の別文面重複を解消）。

設計原則: 質問は**観測可能な事実**だけを問う。「適切か」「妥当か」を残さない。判定不能は安全側（下位・記録のみ）に倒す。`.claude/docs/` は遅延ロード（常駐しない）。

---

## R5. 同趣旨ペア判定 — 統合・件数カウントの前提

feedback 2 件が「同趣旨」か。**2/3 YES で同趣旨**（クラスタの件数は機械カウント、同趣旨 3 件で昇格候補に載せる）:

1. 同一のトリガー操作か（何をしたときに起きたか）
2. 同一の是正行動か（どう直すべきか）
3. 同一の失敗モードか（何が壊れた／壊れかけたか）

「似ているが別の問題」（2/3 に満たない）は無理に統合しない（別々に管理）。

**境界例（是正・失敗モードは操作の字面でなく構造で判定する）**: 「diff を確認せず commit して意図しないファイルが混入」と「PR 本文が実 diff と不一致のまま PR 作成」— トリガー操作は別（Q1 NO）だが、是正はどちらも「成果物確定前に実 diff と突合する」（Q2 YES）、失敗モードはどちらも「宣言・意図と実変更の乖離」（Q3 YES）→ 2/3 で同趣旨。操作の字面差（commit vs PR）だけを見て NO にするのが典型的な誤判定。

## R6. 昇格判定 — feedback を brain に上げるか

**3/4 YES で昇格候補として提示**（最終判断はユーザー）:

1. トリガーを PJ 名・ファイル名・個人環境なしで書き直せるか（一般化可能性）
2. 逆張りテスト: 原則の**否定文**を支持するまともな状況が思いつかないか（思いつくなら原則でなく条件付きルール）
3. 今後 3 セッション以内に再適用する場面を具体的に 1 つ書けるか
4. 既存の brain 原則と重複しないか（重複するなら昇格でなく統合）

**致命クラスの例外（N=1 即昇格候補）**: 以下の 4 カテゴリに該当する教訓は、件数（3 件ルール）を待たず昇格候補にする。**この 4 カテゴリ以外に致命クラスを拡張しない**:

`{ データ喪失, 本番影響, セキュリティ／ガード無効化, 不可逆 git 事故 }`

## R7. 還流 3 分類 — 昇格先の決定

上から順に判定し、**最初に YES になった分類**に置く:

| 分類 | 判定質問 | 行き先 |
|---|---|---|
| **OSS 還流候補** | PJ 名・個人環境を出さずに書けて、業界の誰が読んでも行動が変わるか | sidekick OSS テンプレート（`brain/thinking.md`）への手動 PR |
| **個人 brain 昇格** | 複数 PJ で観測した、または全 PJ に適用したい判断軸か | `~/.claude/brain/thinking.md` |
| **PJ 固有** | その PJ のドメイン・構成・利用者に言及しないと意味が通らないか | `<PJ>/.claude/brain/thinking.md` |

迷ったら下位（PJ 固有）に置き、3 件ルールで上へ昇格させる。判定の一言: **「全 PJ で適用したい判断軸か?」** YES → 個人 brain 以上、NO → PJ 固有。

## few-shot コーパス — 昇格した／しなかった実例

| 事例 | R6 判定 | 結論 |
|---|---|---|
| hook で `echo "$VAR" \| jq` を避け `printf` を使う（POSIX 未定義のバックスラッシュ展開でガード全滅） | Q1✓一般化可 / Q2✓echo でよい状況なし / Q3✓再適用あり / Q4✓重複なし。致命クラス（ガード無効化）で N=1 昇格可 | **OSS 還流候補**（業界共通のシェル落とし穴） |
| 数値・API 名・バージョンを断定する前に「一次ソースを当該セッションで見たか」を自問する | Q1✓ / Q2✓見ずに断定してよい状況なし / Q3✓ / Q4✓ | **個人 brain 昇格**（複数 PJ 横断の思考規律・業界固有でない） |
| 対話 UI（選択肢の文言含む）を利用者の言語に統一する | Q1✗トリガーが PJ 利用者の言語前提 / Q2✓ / Q3✓ / Q4✓ → 3/4 だが一般化質問が NO | **PJ 固有**（PJ の利用者に言及しないと意味が通らない） |
| 特定ライブラリの特定バージョンの既知バグ回避コード | Q2✗そのバージョンを離れれば不要（否定文を支持する状況が容易） → 条件付きルール | **昇格せず**。実装メモ（`reference_*.md`）に記録 |
| 特定実行環境でのみ必要なツール設定（例: ある仮想化環境でのテスト runner の pool 指定） | Q1✓PJ 名なしで書ける / だが「業界の誰が読んでも行動が変わる」には**その環境の利用者限定で届かない** | **個人 brain 昇格**（複数 PJ 横断の環境ノウハウ。環境条件付きの知見は OSS 還流まで上げない） |
| 1 回きりのタイポ修正 | R5 で同趣旨クラスタを作れない（単発・再現手順が一般化不可） | **feedback 化しない**（過剰蓄積防止） |

**読み方**: 昇格の分かれ目は R6-Q1（一般化）と Q2（逆張り）。この 2 問が NO なら下位分類か記録のみに落とす。致命クラス 4 カテゴリだけは件数を待たない。

## 統合ルール（feedback 圧縮）

R5 で同趣旨と判定した feedback が複数ある場合:

1. 最も具体的・包括的な feedback をベースにする
2. 他の feedback の事例・コンテキストを追記する
3. 統合元は削除せず、冒頭に `<!-- 統合済み: feedback_xxx.md に統合 -->` を追記
4. MEMORY.md の索引も更新する

**圧縮しないもの**: 昇格済みでも経緯記録として feedback ファイル自体は残す（索引に「昇格済み」を明記）。

## 記録アクション — フラグを立てる、即更新しない

分類が決まったら **feedback_*.md + MEMORY.md Backlog に還流タグ**（`[OSS 還流候補]` / `[個人 brain 昇格]` / `[PJ 固有]`）を立てるだけ。

**重要: その場で brain / OSS テンプレートを更新しない。** 実際の昇格・還流は棚卸し（`/weekly-inventory` Step 3-4）でまとめて行う（蓄積 → パターン検出 → 昇格 → 還流の順）。OSS 還流は手動 PR（自動同期しない）。
