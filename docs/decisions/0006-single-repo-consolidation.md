# ADR-0006: 開発と配布を単一リポに統合する

## ステータス

採用（2026-06-13）— 方針確定。物理統合（履歴・残コンテンツの移行、design ダイジェスト整備）は段階実施。

二リポ運用の決定（本 ADR の旧版）を supersede する。

## 背景

sidekick（開発リポ）と claude-code-sidekick（配布リポ）を分離する二リポ運用には、以下の構造的問題がある。

1. **dogfood が構造的に成立しない**: 保守者が日常的に使うのは開発リポであり、配布リポは誰も日常使用しない。配布リポに固有の不具合（stale なテンプレート、旧モデルの残骸等）が、誰にも使われないまま無検知で出荷される。dogfood の対象（開発リポ）と配布の対象（配布リポ）が分離しているため、配布物の品質保証が dogfood で担保されない。

2. **同期ドリフトの実害**: 一方向同期（開発リポ → 配布リポ）はドリフトを生む。配布リポを直接編集すると開発リポと乖離し、その乖離が検知されないまま配布される。配布リポの索引が存在しないファイルを指す、配布リポのドキュメントが開発リポの最新状態を反映しない、といった不整合が蓄積する。

3. **固有情報フィルタの検知遅れ**: 二リポは同期のたびにプロダクト/プロセス分離フィルタを適用するが、フィルタ漏れの検知は同期サマリの目視に依存する。漏れた場合の検知が遅れる。

## 検討内容

| 選択肢 | dogfood の構造的保証 | 同期コスト | 固有情報の漏洩防止 |
|--------|------|------|------|
| A: 二リポ維持 | 名目的のみ（配布物は dogfood されない） | 高（同期 + ドリフト検知） | 同期フィルタ依存（漏れの検知が遅い） |
| **B: 単一リポ統合（採用）** | 構造的に保証（保守者が配布物を直接使う） | ゼロ | local 層 + 強制 hook で担保 |
| C: ブランチ分離（1 リポ内） | 部分的 | 中（ブランチ間差分管理） | 固有情報が同一リポに同居 |

### 単一リポでの固有情報漏洩防止

配布物に固有情報を絶対に含めないことを、二段で担保する。

| 層 | 手段 |
|---|---|
| 退避 | 固有情報は git 非追跡の local 層（`CLAUDE.local.md` / auto-memory / `settings.local.json`）に置く |
| 強制 | 公開ファイルへの固有情報混入を pre-commit hook（`scan_pii` の強制層昇格）で物理ブロックする |

## 決定

**開発と配布を claude-code-sidekick の単一リポに統合する。** 保守者は配布リポを直接 dogfood する。

### 1. リポ構成

- claude-code-sidekick を開発・配布双方の canonical リポとする
- 一方向同期スキル（`/sync-oss`）は廃止する
- 開発リポ（sidekick）は統合先にたたみ、アーカイブする（物理統合は段階実施）

### 2. 保守者専用スキルの行き先

| スキル種別 | 行き先 |
|---|---|
| リリース（`/release`） | 配布リポ自身のリリース用に残す |
| 保守者専用（外部連携・公式追従等） | 個人スキル領域 `~/.claude/skills/` に退避（配布物に含めない） |
| 一方向同期（`/sync-oss`） | 廃止 |

### 3. ADR の扱い

- 配布リポを ADR の canonical home とする
- 下流 PJ（fork）には番号付き ADR を配布しない原則（ADR-0014）を維持する。fork 時の `/setup` 自動 strip + 評価者向けの設計思想ダイジェスト（番号なし、現行思想のみ）で担保する

### 4. 固有情報の強制層

- 単一リポ化の前提条件として、`scan_pii` を pre-commit hook（強制層）に昇格する

## 理由

1. **dogfood の構造的保証を最優先する**: 二リポの「dogfood が強制される」という利点は名目的であり、実際には配布物が dogfood されず stale 出荷を招く。保守者が配布物を直接使う構成が、配布品質を構造的に保証する
2. **ドリフトを原理的に消す**: 単一リポでは開発と配布が同一であり、同期ドリフトが発生しない
3. **漏洩リスクは強制層で担保する**: 同期フィルタ（目視依存・検知遅れ）に代えて、pre-commit hook（物理ブロック）で固有情報混入を止める。仕組み化の3層でいう「認知」ではなく「強制」で担保する

## 却下した案

- **二リポ維持**: dogfood が名目的で、配布物の stale 出荷とドリフトの実害が解消されない
- **ブランチ分離（1 リポ内）**: 固有情報が同一リポに同居し、ブランチ間の差分管理が煩雑

## 影響

### 段階実施

物理統合は方針確定後に段階実施する。

- `/sync-oss` スキルの廃止
- 保守者専用スキルの `~/.claude/skills/` への退避
- 開発リポ残コンテンツの配布リポへの移行、開発リポのアーカイブ
- 評価者向け設計思想ダイジェスト（番号なし）の整備
- `scan_pii` の pre-commit hook 化（前提条件）

### 関連 ADR の再整理

- ADR-0014（ADR 非配布）: 原則は維持。担保機構を「同期フィルタ」から「fork 時 strip + 設計思想ダイジェスト」に移す
- ADR-0015（下流 PJ の ccs 不意識運用）: 単一リポでも下流は配布リポ 1 つだけを意識すればよく、原則に整合
- ADR-0001（配信方式）: GitHub Template + Releases + `/adopt-sidekick-update` の配信は変わらない
