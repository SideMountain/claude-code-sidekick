# ADR-0034: UX 導線スキャンスキル（/ux-scan）の追加

- Status: Accepted（v0.17.0 で実装）
- Date: 2026-07-20

## Context

AI 支援開発でコード生成が高速化した一方、UI 導線の品質（機能への到達コスト・迷いの少なさ）は人手レビューの主観に依存したままで、回帰も検知できない。テスト・型・lint が担う「機械判定できる合否」の UX 版が存在しない。

計測可能な代理指標は確立している: KLM / GOMS（操作列からのコスト予測、1980s）に頻度加重を掛ければ、「毎日の操作が深い」= 欠陥 /「月 1 の操作が深い」= 正常、を機械的に順位付けできる。クリック数の絶対値を閾値にする「3 クリックルール」は反証済み（NN/g）のため採用せず、頻度 × 到達コストの会計を採る。

## Decision

1. **タスク型でなく対話型スキル**として `/ux-scan` を追加する。初回のタスクリスト（Top10・頻度・理論最短）は人間確定値であり、合意までスキャンに進まない。重い導線トレースのみ Agent 委譲（Return Contract 付き）
2. **静的モードを主体**にする: ルート定義 → ナビ → ハンドラのコードトレースで手数・分岐数を計数（file:line 根拠必須）。実ユーザー・実行環境なしで回るため、リリース前・CI 後・改修前後のどこでも実行できる。ブラウザエージェントによる動的計測は環境がある PJ のみの任意拡張
3. **ルーブリックは導入時に凍結**する。同一物差しでの再実行 = UX の回帰テストとして機能させ、スコア増を「回帰」として報告の先頭に置く（テストの赤と同じ扱い）
4. **処遇 3 択を出力に含める**: 磨く（判断が本体）/ 消す（高頻度 × 裁量ゼロ → 自動化で導線自体を無くす）/ 機械向け口に落とす（消費者が別システム / エージェントなら API / MCP を第一級に）。導線の最適化だけでなく「その導線が人間用 UI として存在すべきか」を判定対象にする
5. 実装 / レビュー時の判断軸は **`.claude/rules/ux-flow-friction.md.example`（opt-in）**として配布する。UI を持たない PJ に常駐コストを課さないため、既定では `.example`（`task-db-integration.md.example` と同じ規約）

## Consequences

- スキル 1 本 + rules 雛形 1 本の追加。既存スキル・hooks への変更なし
- PJ 側に生まれるインスタンス: `docs/ux-tasks.md`（人間確定値を含む仕様の一部）と `docs/ux-scans/`（計測履歴）
- ルーブリック凍結の副作用として、計数規約を変えたい場合はベースライン取り直し（別サイクル）になる
- 却下した代替案: (a) 良さを合成した単一 UX スコア — 主観の合成で再現性がなく回帰テストにならない (b) 動的モード主体 — 環境・資格情報の前提が重く、テンプレートの既定にできない (c) rules を既定配布 — UI なし PJ への常駐コストが原則（retrieve > resident）に反する
