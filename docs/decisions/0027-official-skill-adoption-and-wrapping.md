# ADR-0027: 公式スキル採用とラップ配布（OS 層 + 指揮者への縮約）

## ステータス

採用（2026-07-04、方針決定・実装は段階的に実施）。前提: ADR-0007（思考 OS ポジショニング）、ADR-0018（北極星）、ADR-0023/0024/0025（文脈経済・budget-gate）。

## 背景

ccs の目的は「人間の判断軸（brain）に沿って、AI が自律的かつ安全に動くハーネス」である。この目的に対し、2 つの環境変化が重なった。

1. **公式スキルの成熟**: Claude Code 本体が code-review（effort 段階 + クラウド多エージェント）・verify・simplify・goal（完了条件の複数ターン自動実行）・loop・schedule・batch・plan mode 等を提供するようになった。ccs が自前で維持してきた実行機構（特に review 系 6 スキル）は公式と重複し、二重投資になっている。
2. **モデル tier 変動への耐性不足**: 全スキル棚卸しで、判断ポイント約 60 箇所が prose 裁量＝モデルの解釈力への暗黙依存と判明した。実行機構を自前で持つほど、モデル交代時に劣化する面積が広がる。

公式側の拡張点は裏取り済み: REVIEW.md によるレビュー観点の注入（公式サポート・最優先で system prompt に注入）、プロジェクト定義による公式スキルの上書き（優先度: enterprise > personal > project > bundled）、スキル存在のバージョン判定。PJ 規範を注入しながら公式の機構に乗る手段が公式に存在する。

## 決定

### 決定 1: 責務の再定義 — ccs は「OS 層 + 指揮者」、実行部品は公式

- **OS 層（ccs が自前で持ち続けるもの）**: brain（判断軸）/ CLAUDE.md + rules(規範)/ hooks(強制層)/ 知識パイプライン（close-chat・weekly-inventory・inventory）/ 文脈経済（token-audit・budget-gate）/ 配布系（setup・release・adopt）
- **指揮者**: auto-implement を、公式部品（plan mode → goal → 実装 → verify → code-review）を brain と HARD 制約の下で組み合わせる orchestrator に刷新する
- **実行部品**: レビュー・検証・反復・スケジュール・計画は公式スキルを採用する

### 決定 2: ラップ配布 — 公式に「PJ 規範」を注入する薄い層だけを配る

公式スキルをそのまま使うのではなく、PJ 規範（HARD ルール照合・ADR 整合・総合判定 rubric・REVIEW.md）を注入する薄いラッパーとして配布する。review 系 6 スキルは 1 アダプタ + REVIEW.md に縮退する。ラッパーには機構を実装しない（機構は公式、規範は ccs）。

### 決定 3: 境界層 — 公式依存は失敗する前提で設計する

公式スキルはバージョン差で欠け、予告なく挙動が変わりうる。存在チェック（バージョン下限判定）+ 不在時 fallback（明示 WARN。silent 破綻禁止）の境界層を hook-helpers に置き、公式依存の知識をこの 1 箇所に閉じる。

### 決定 4: 鮮度 watch — 採用方針の持続機構

weekly-inventory / news-upstream に「公式スキル差分チェック」を常設し、公式の新機能・挙動変更とラッパーの gap を検知して skills/rules を刷新し続ける。公式採用は一度きりの移行ではなく、継続的な追随プロセスとして運用する。

### 決定 5: 残すコアの判断は 4 形態に外部化する

OS 層に残る暗黙判断は few-shot（実例模倣）/ rubric（YES/NO + 閾値）/ 決定的スクリプト / harness 補強（敵対検証・premise-check の明示ステップ化）に外部化し、モデル tier に依存しない品質下限を構造で担保する（ADR-0023 決定 3 の具体化）。

## 影響

- スキルの仕分け（維持 / アダプタ化 / 薄型化 / 刷新）と実装順は決定 1・決定 2 の方針に沿って段階的に実施する
- 下流 PJ: /setup が REVIEW.md 生成と公式スキルのブートストラップを担い、下流は構成を意識せず恩恵を受ける（ADR-0018 北極星と整合）
- Claude Code のバージョン下限の明示が必要になる（境界層の feature gate で緩和）
- 旧 review 系スキルは deprecation 期間（1 リリース）を挟んで撤去し、下流移行ガイドを添付する（ADR-0009 の取り込み設計に従う）

## 代替案と却下理由

- **全スキル自前維持の継続**: 却下。公式と重複する機構の維持コストと、モデル解釈依存の判断品質という二重負担。公式の進化速度に自前実装で追随し続けるのは非現実的。
- **公式スキルへの完全依存（ラップなし）**: 却下。公式は PJ 規範（HARD ルール・判断軸・強制層・知識パイプライン）を知らない。安全と規範の注入層こそが ccs の存在理由であり、ここを手放すと「思考 OS」の位置づけ（ADR-0007）が崩れる。
- **公式スキルの fork（コピーして改変）**: 却下。上流の更新を取り込めず陳腐化する。公式に注入点（REVIEW.md・プロジェクト定義の上書き優先度）がある以上、ラップで足りる。
