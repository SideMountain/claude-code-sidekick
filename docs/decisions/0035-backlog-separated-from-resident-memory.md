# ADR-0035: 積み残しは常駐メモリから分離する（`MEMORY.md` / `BACKLOG.md`）

- ステータス: 承認
- 日付: 2026-07-31
- 関連: ADR-0022（intake routing）、ADR-0023（文脈経済）

## 背景

`MEMORY.md` は**毎セッション自動ロードされる**。そこに 3 つの異なる性質のものを同居させていた。

| 中身 | 変化速度 | 毎セッション読む必要 |
|---|---|---|
| 索引（Memory Index） | 遅い | ある |
| Active Work | **最速**（並行セッションが同時に書く） | ある |
| **Backlog（積み残し）** | 中 | **ない** — 必要なときだけ |

積み残しは「次のセッションで参照するかもしれない」ものであって、**毎回読む必要はない**。
それを常駐ファイルに置くと、使わない情報が常駐コストを食う。運用実測では
**Backlog が `MEMORY.md` 全体の 4 割**に達し、読み取り上限に到達しかけた。

このとき圧縮で凌ごうとすると失敗する。並行セッションが積む速度が圧縮の速度を上回るため、
**1 日のうちに 3 回圧縮して 3 回押し戻された**。サイズ管理では解けない。

さらに Backlog の内容を分類すると、**3 分の 1 が Issue クラス**（他人が拾える具体的作業単位）だった。
判定基準は ADR-0022 の intake routing に既にあり、しかも**当人が「［Issue推奨］」と自らタグを
付けていながら起票していない**項目が複数あった。認知はあるのに行動が伴っていない状態で、
起票済みなのに Backlog 側が残った重複も生じていた。

## 決定

1. **積み残しは `BACKLOG.md`（auto-memory 内・常駐しない）に置く。** `MEMORY.md` は
   **索引 + Active Work** に限定する。消費側（`/inventory` `/close-chat` `/weekly-inventory`）が
   必要なときに読む。

   これは容量対策ではなく**寿命と読む頻度による分割**である。分けておけば、Backlog が
   どれだけ伸びても `MEMORY.md` は伸びない。サイズ問題が構造的に消える。

2. **`MEMORY.md` の Active Work は 1 エントリ 1 行。** 詳細（実測値・判断の経緯・落とし穴）は
   topic ファイルに置き、Active Work からは参照だけ張る。1 エントリが数行に膨らんだら、
   それは topic に置くべき内容が混ざっているサインとして扱う。

3. **`［Issue推奨］`と書いて済ませない。** そう判定した時点で起票する。判定と行動を分けると
   Backlog が Issue の代替物として溜まる。`/weekly-inventory` はこのタグの滞留を
   **棚卸しの先頭に強制表示**し、`/close-chat` は積む前に起票を促す。

4. **`/weekly-inventory` は圧縮の前に増加の主因を分類する。** `MEMORY.md` が上限に近づいたとき、
   ①Backlog の混入 ②Active Work のエントリ膨張 ③完了済みの残置 のどれかを特定してから手を入れる。
   圧縮を先にやると原因が残り、翌週同じ位置に戻る。

5. **並行セッション下では他セッターの Active Work を独断で削らない。** 削る候補として提示し、
   判断を仰ぐ。圧縮が追いつかない状況は正常な状態として扱う。

## 却下した案

### 案 A: `MEMORY.md` を定期的に圧縮して収める

却下理由: 並行セッションが積む速度が圧縮の速度を上回る。実測で 1 日に 3 回押し戻された。
また圧縮は「何を捨てるか」の判断を毎回要求するため、他セッションの記録に手を入れる判断を
繰り返し発生させる。**構造で解けるものを規律で解こうとしている。**

### 案 B: Backlog を GitHub Issues に全面移行する

却下理由: 「未成形の検討残」「working context」は Issue にする単位に達していない。
全部 Issue にすると Issue が雑多になり、逆流ループ（Issue → 実装）の信号が薄まる。
ADR-0022 の二トラック（backlog / Issue）は維持したまま、**振り分けの実行を強制する**方が正しい。

### 案 C: `MEMORY.md` に置いたまま行数上限だけ厳しくする

却下理由: 上限を厳しくしても「どれを消すか」の問題が残る。かつ Backlog は本来
**消してはいけない**もの（次セッションのための記録）なので、上限で殺すのは目的に反する。

## 影響

- `auto-memory` の構成に `BACKLOG.md` が加わる（`MEMORY.md` と同じディレクトリ・git 非追跡）
- `/close-chat` は追記先を `BACKLOG.md` に変更する
- `/inventory` `/auto-implement` は読み込み元を `BACKLOG.md` に変更する。
  **`BACKLOG.md` が無い PJ では後方互換として `MEMORY.md` の `## Backlog` を見る**ので、
  既存 PJ は移行しなくても壊れない
- `/weekly-inventory` のスナップショットに bytes・Issue 未起票の滞留件数・
  `MEMORY.md` への Backlog 混入の検知を追加する
- ADR-0022（intake routing）の判定基準そのものは変えない。置き場の名前と、
  判定を実行に結びつける検知層を足しただけ

## 移行

既存 PJ は次の `/weekly-inventory` で移す。`MEMORY.md` の `## Backlog` セクションを
`BACKLOG.md` に切り出し、`MEMORY.md` 側にはポインタを 1 行残す
（並行セッションが積み直さないよう「ここに積まない」と明記する）。
