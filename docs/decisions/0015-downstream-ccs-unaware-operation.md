# ADR-0015: 下流 PJ の ccs 不意識運用原則

## ステータス

採用（2026-05-05）— v0.7.4 で実装。

## 背景

ADR-0014 で「sidekick の ADR は下流 PJ に配布しない」方針を確立し、`docs/decisions/` を `/adopt-sidekick-update` の取り込み対象から除外した。これにより新規取り込み時の ADR 混入は構造的に防げるようになったが、運用面の整理が不十分なまま残った。

1. **既存残骸の手動清掃**: ADR-0014 適用前に下流 PJ に取り込まれた sidekick 由来 ADR ファイルは、リリースノートの「⚠️ 取り込み時の注意」セクションを下流 PJ オーナーが読んで手動 `rm` する必要があった
2. **手動手順の見落とし**: 下流 PJ オーナーがリリースノートを読まないと残骸が残り続ける
3. **概念の漏出**: 下流 PJ オーナーが運用上「sidekick リポ」「ccs リポ」の存在を意識する必要があった（手動清掃コマンドに `docs/decisions/0007-thinking-os-positioning.md` のような sidekick 内部 ADR ファイル名が登場する等）

下流 PJ オーナーから見た理想の運用は、「`/inventory` と `/adopt-sidekick-update` を実行するだけで、必要な変更が取り込まれ、不要な残骸も自動的に消滅する」状態である。

## 検討内容

### 自動清掃ロジックの識別方式

下流 PJ で「sidekick 由来 ADR ファイル」を識別する方式を比較する。

| 方式 | 識別手段 | 実装コスト | 副作用 |
|--------|---------|-----------|---------|
| **ファイル名照合 + 内容比較（採用）** | 下流から `git ls-tree ccs/main -- docs/decisions/` で sidekick の ADR ファイル名を取得し、下流 PJ 内の同名ファイルとファイル内容を完全比較。完全一致 = 由来確定 | 低 | ccs リモート fetch が前提（既に `/inventory` で実施済み） |
| Manifest 方式 | sidekick リポに ADR 一覧の manifest ファイルを git 管理。下流が manifest を取得して照合 | 中 | 新ファイル管理コスト |
| Frontmatter タグ方式 | sidekick の各 ADR に `provenance: sidekick` frontmatter を追加。下流が ADR 内容で判別 | 低 | 既存 ADR 全件の編集が必要 |
| git history 方式 | 下流 PJ の `git log` 解析で「ccs リモートから入ったコミット」を判定 | 高 | history が消えると失敗、複雑 |

### 削除事故の予防

PJ 固有 ADR と sidekick 由来 ADR が偶然同じファイル名になる可能性がある（例: 番号衝突）。**ファイル内容の完全一致確認**を必須にすることで、内容が異なる場合は「PJ 固有 ADR の可能性」として削除候補から除外する。

### 手動手順のリリースノート記載の扱い

下流 PJ オーナーに手動操作を強いる手順は、リリースノートに記載しない。手動操作を必要とする変更がある場合は、その手順を機械化（スキル / hook / 自動清掃）してからリリースする。

## 決定

下流 PJ の運用は以下の 4 原則に従う。

1. **完結性**: `/inventory` と `/adopt-sidekick-update` の実行だけで、取り込みと残骸清掃が完結する
2. **自動清掃**: 過去の取り込みで残った sidekick 由来 ADR ファイルは、`/adopt-sidekick-update` が自動検知し、デフォルトで削除する
3. **不可視性**: 下流 PJ オーナーは sidekick リポ / ccs リポを直接参照しなくても運用が完結する
4. **手動手順禁止**: リリースノートに「下流 PJ で `rm` を実行してください」のような手動清掃手順を記載しない。新たな手動操作が必要になった場合は、その操作を機械化してからリリースする

### 実装

v0.7.4 で以下を実装する。

1. **`/adopt-sidekick-update` Step 6.4d 拡張**: ファイル名照合 + 内容比較方式で残骸 ADR を自動検知し、デフォルト `[Y]` で削除提案する。完全一致しないファイルは「PJ 固有 ADR の可能性」として削除候補から外す
2. **`/setup` Step 1 改修**: 新規 PJ セットアップ時に `docs/decisions/` を sidekick 側からのコピー対象から除外する（ADR-0014 の `/setup` 側への反映）
3. **`references/release-format-spec.md` 改修**: 「⚠️ 取り込み時の注意」セクションのテンプレートを削除し、`/release` スキルが手動手順をリリースノートに含めない方針を明示する

## 結果

### メリット

- 下流 PJ オーナーの operational complexity が大幅に低減する
- 過去取り込みの残骸が構造的に消滅する
- リリースノート作成時に手動手順を書かなくて済むため、リリースノートが「変更内容の説明」に純化する
- 新規 PJ セットアップ時にも残骸が混入しない（`/setup` 改修により ADR-0014 が完全に効く）

### デメリット・リスク

- 自動削除は破壊的操作のため、識別ロジックに誤りがあると PJ 固有 ADR を消す事故が起きうる
  → ファイル内容の完全一致確認で回避する
- 下流 PJ で `git fetch ccs` がまだ実行されていない（`/inventory` を一度も走らせていない）状態だと、ccs リモート参照ができず自動清掃が動かない
  → `/adopt-sidekick-update` の前提として `/inventory` 実行を要求する記述を追加する

### 後方互換性

- 既に v0.7.0〜v0.7.3 を取り込んでいる下流 PJ では、v0.7.4 取り込み時に Step 6.4d の自動清掃が初回実行され、残骸が一度に消える
- v0.6 系から飛び石で v0.7.4 を取り込む下流 PJ でも、Step 6.4d が同じく走るため、過去どの sidekick バージョンを取り込んでいても残骸が清掃される
