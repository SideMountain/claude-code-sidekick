# ADR-0002: 自動実行のブラックリスト方式と2レーン制

## ステータス

承認済み（2026-04-07）

## 背景

現在のsidekickは「ホワイトリスト方式」で自動実行を制御している。確認不要リストに載っている操作のみ自動実行し、それ以外は確認を求める。この方式は安全だが、承認待ちが頻発してオーナーがボトルネックになる。

また、タスクの重さによって最適なフローが異なる:
- 軽い修正（色変更等）: 自動で回せるはず
- 重い機能追加（サブスク機能等）: 対話が必要

シミュレーションの結果、1つのフローで全タスクを扱うのは破綻することが判明。

## 検討内容

### 自動実行の制御方式

| 選択肢 | デフォルト | 安全性 | 速度 | ボトルネック |
|--------|-----------|--------|------|------------|
| ホワイトリスト（現状） | 止まる | 高い | 遅い | なりやすい |
| **ブラックリスト（提案）** | 進む | 中（禁止漏れリスク） | 速い | なりにくい |

### タスクの流し方

| 選択肢 | メリット | デメリット |
|--------|---------|-----------|
| 全て Issue 駆動 | 統一的 | 重い機能でIssueが破綻（仕様確定に対話が必要） |
| 全て Tasks DB 駆動 | 対話重視 | 軽い修正にオーナーの手動介入が必要 |
| **2レーン制** | 重さに応じて最適なフロー | 2レーン間のタスク重複リスク |

### STGマージの自動化範囲

| 選択肢 | メリット | デメリット |
|--------|---------|-----------|
| 手動マージのみ | 安全 | 遅い |
| **review OK + テスト通過で自動** | 速い | レビュー品質への依存 |
| 無条件自動 | 最速 | 危険 |

## 決定

### 1. ブラックリスト方式に段階的移行

```
禁止（hooksで物理ブロック。例外なし）:
  - PRDデータベースへの書き込み
  - 保護ブランチへの直接push
  - .env の DATABASE_URL 変更
  - rm -rf
  - prisma db push

承認必須（不可逆な操作）:
  - PRDマージ/デプロイ
  - PRD DBマイグレーション
  - PRD DB SELECT（読み取りでも確認）

それ以外 → 全て自動実行
```

移行は一括ではなく、現在の「確認必須」リストを1項目ずつ検証しながら自動実行に移行する。

### 2. 2レーン制

```
Lane 1: Issue駆動（軽〜中のタスク）
  Slack → Issue → 自動実装 → /review → STG自動マージ → Playwright → レポート → PRD判断
  オーナーの介入: PRD判断のみ

Lane 2: Tasks DB駆動（重いタスク）
  オーナー → Tasks DB → Claude Code対話 → 設計 → 実装
  オーナーの介入: 仕様確定 + 設計判断
  ※ 仕様確定後のサブタスクは Lane 1 に流せる
```

### 3. STGまで自動マージ

/review OK + テスト通過を前提条件として、STGマージは自動。PRDマージのみオーナーの手動判断。

### 4. 重複検知

/inventory で Tasks DB と GitHub Issues を横断照合し、類似タスクの重複を検知・警告する。

## 理由

- ブラックリスト方式は thinking.md の「70%の確信で動く。ただし不可逆な操作は慎重に」と整合する
- 2レーン制はシミュレーション（ケース1-3）で実際の破綻パターンを確認した上での判断
- 段階的移行は「禁止漏れ」のリスクを最小化する
- 重複検知は2レーン間のタスク衝突を防ぐ安全策

## 影響

- CLAUDE.md §2 の構造が「確認不要リスト + 確認必須リスト」から「禁止リスト + 承認必須リスト」に反転
- hooks の役割が「ガイド」から「ブラックリストの強制層」に明確化
- /inventory に重複検知ステップを追加
- Lane 1 用の GitHub Actions テンプレート（AI不要な部分: CI/CD、Playwright、通知）
- Lane 2 は既存の Tasks DB 連携フローを維持
