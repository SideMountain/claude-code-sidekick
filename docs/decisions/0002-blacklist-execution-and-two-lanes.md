# ADR-0002: 自動実行のブラックリスト方式と2レーン制

## ステータス

承認済み（2026-04-07）

## 背景

sidekick の初期バージョンは「ホワイトリスト方式」で自動実行を制御していた。許可リストに載っている操作のみ自動実行し、それ以外は確認を求める。安全だが、承認待ちが頻発してオーナーがボトルネックになる。

また、タスクの重さによって最適なフローが異なる:
- 軽い修正（UIの色変更等）: 自動で回せるはず
- 重い機能追加: 対話が必要

シミュレーションの結果、1つのフローで全タスクを扱うのは破綻することが判明した。

## 検討内容

### 自動実行の制御方式

| 選択肢 | デフォルト | 安全性 | 速度 | ボトルネック |
|--------|-----------|--------|------|------------|
| ホワイトリスト（現状） | 止まる | 高い | 遅い | なりやすい |
| **ブラックリスト（提案）** | 進む | 中（禁止漏れリスク） | 速い | なりにくい |

### タスクの流し方

| 選択肢 | メリット | デメリット |
|--------|---------|-----------|
| 全て Issue 駆動 | 統一的 | 重い機能で破綻（仕様確定に対話が必要） |
| 全て対話駆動 | 対話重視 | 軽い修正にも手動介入が必要 |
| **2レーン制** | 重さに応じて最適なフロー | 2レーン間のタスク重複リスク |

## 決定

### 1. ブラックリスト方式

```
禁止（hooks で物理ブロック。例外なし）:
  - 本番データベースへの書き込み
  - 保護ブランチへの直接 push
  - .env の DATABASE_URL 変更
  - rm -rf
  - prisma db push

承認必須（不可逆な操作）:
  - 本番マージ/デプロイ
  - 本番 DB マイグレーション
  - 本番 DB SELECT（読み取りでも確認）

それ以外 → 全て自動実行
```

### 2. 2レーン制

```
Lane 1: Issue 駆動（軽〜中のタスク）
  Issue → /auto-implement → /review → STG マージ → テスト → 本番判断
  オーナーの介入: 本番マージ判断のみ

Lane 2: 対話駆動（重いタスク）
  対話 → 設計 → 実装
  オーナーの介入: 仕様確定 + 設計判断
  ※ 仕様確定後のサブタスクは Lane 1 に流せる
```

### 3. STG まで自動マージ

`/review` OK + テスト通過を前提条件として、STG マージは自動。本番マージのみオーナーの手動判断。

## 理由

- ブラックリスト方式は「70% の確信で動く。ただし不可逆な操作は慎重に」の原則と整合する
- 2レーン制はシミュレーションで実際の破綻パターンを確認した上での判断
- 段階的移行により「禁止漏れ」のリスクを最小化できる

## 影響

- CLAUDE.md §2 の構造が「確認不要リスト + 確認必須リスト」から「禁止リスト + 承認必須リスト」に反転
- hooks の役割が「ガイド」から「ブラックリストの強制層」に明確化
- `/inventory` に重複検知ステップを追加
