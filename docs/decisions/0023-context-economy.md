# ADR-0023: 文脈経済（Context Economy）— rate-cap 内で精度を落とさず長く稼働する

## ステータス

採用（2026-06-23、原則を決定・実装は段階的 follow-up）。PR1 = 本 ADR + `rules/context-economy.md` + `/token-audit` skill。PR2 = 自律ループ設計 ADR（ledger + budget-gate）。

## 背景

多エージェント fan-out（ultracode 的フロー）は母数最大化・敵対検証で精度を上げる強力な手段だが、消費トークンが膨大になる。サブスクリプションの利用上限（rolling window の rate-cap）がある環境では、これを「垂れ流す」と早期に枯渇し、長時間稼働や自律実行（`/auto-implement`）が継続できない。**制約は資金ではなく cap**であり、目標は「cap あたりの有効仕事量」と「枯渇させずに長く動かすこと」。

設計の前提となるコスト機構（**正確な数値は公式非開示のため実測前提**だが、構造は確度高）:

- rate-limit は実質**トークン量ベース**（時間表示は簡略化）。重い作業ほど早く枯れる。
- **キャッシュ読込は base input の約 1/10**。サブスクリプションの TTL は長め。cache を温存し続けるほど実消費が下がる。
- **会話履歴のコストは概ね O(n²)**（各ターンが全履歴を再投入）。cache は安定 prefix には効くが、**伸び続けるメッセージ層には効かない**。
- **compaction だけがメッセージ層を削れる**唯一の手。
- **model / effort の切替は cache を全破棄**し full reprocess を招く。
- **fork は親の cache を継承**でき、同等タスクで named subagent より初回が大幅に安い。
- **subagent / workflow は同じ cap から引かれ**、各自が system prompt を再ロードするため掛け算的に積む。
- **出力は入力より高単価**、拡張思考（thinking）は出力として課金され effort で大きく変動する。

### オーナー方針（本 ADR の制約条件）

- **cap 消費は減らすが、精度は落とさない（ハード制約）。** 節約は最適化、安全と難所は聖域。
- **モデルの自動選択（tiering）よりも、「モデルを呼ぶ時に不要な文脈を渡さない（汚染防止）」を優先する。** 文脈の純度向上はコストと精度を同時に改善する最も安全なレバーであり、モデル単価の引き下げ（精度リスクを伴う）より上位に置く。

## 決定

### 決定 1: 文脈経済の 7 原則（背骨）

優先順位はオーナー方針に従い、精度に安全なものを上位に置く。

1. **per-call context hygiene（最優先）** — (sub)agent / モデルを呼ぶたび、**必要なものだけ**渡す。無関係な文脈は渡さない。ノイズ除去はコストと精度を同時に改善する。
2. **cache を壊さない** — model / effort はセッション（自律では各サイクル）の頭で固定。安定 prefix を前方に。同等タスクは named subagent より fork。
3. **文脈は資産ではなく負債** — 既定は retrieve > resident（常駐は例外・要正当化）。一度読んだものは再読込しない。
4. **O(n²) は外部化 + compaction で断つ** — 長時間稼働では状態を disk に外部化し、メッセージ層を compaction で抑える（詳細は PR2 の自律ループ ADR）。
5. **最大の節約は会計に出ない** — 良い制約 1 行が誤実装の手戻り（数千トークン）を消す（spend-to-save）。厚い計画・検証・一括文脈渡しがトータルで安いことがある。
6. **lossy な機構には必ず検知層** — 要約・縮退・観点スキップで落としたものは silent drop せず、Issue / ledger に明示する。
7. **認知 → 強制 → 検知で仕組み化** — 原則の周知だけでは漏れる。hook 化できる機構（cache 規律・fan-out cap・Read-once）は強制層へ、計測（`/token-audit`）は検知層へ。

### 決定 2: 精度はハード制約・聖域を明示

トークン効率を理由に省略してはならない核を定義する。**安全ルール（HARD 規則）・本番保護・不可逆操作のガード・設計判断の「なぜ」**。これらは enforcement 層（hooks / permissions）にあるものを含め削減対象外。節約は目的関数、安全は実行可能領域の境界であり、最適化が制約を破ることはない。

### 決定 3: model tiering は補助レバー（既定は精度優先）

モデルの自動ダウングレードは本ドクトリンの中核に**置かない**。

- 既定は精度優先。明確に機械的なサブタスク（列挙・検索・決定的検査の結果整形）に限り下位モデルを使ってよい。
- **難所（設計判断・曖昧な root-cause・矛盾裁定・セキュリティ・最終 judge）は必ず上位モデルを使う（不変条件）。**
- cap / model の重み付けは非公開のため、tiering の効果は**実測してから**判断する（`/token-audit` の計測プロトコル）。未実測の一律ダウングレードは禁止。

### 決定 4: 配布と段階性（stack 非依存・無意識運用）

本ドクトリンは特定スタックに依存しない普遍サイクルの一部として配る（ADR-0021 の opt-in 原則、ADR-0018 の北極星「下流はハーネスを意識せず恩恵を受ける」と整合）。下流は規律と `/token-audit` の恩恵を、追加設定なしで受けられる。重い強制機構（fan-out cap・compaction 自動化）は段階的に hook 化し、過剰な設定要求をしない。

## 影響

- 新規: `.claude/rules/context-economy.md`（安全コア規律・per-call hygiene 中心）、`.claude/skills/token-audit/`（計測・検知層）。
- 既存との関係: `context-management.md`（行数予算・compact 閾値）の上位概念。`skill-agent-design.md` の隔離 + Return Contract を「per-call hygiene」として原則化。
- 非目標（PR1）: モデル自動ルーティングの実装、自律ループの ledger 実装（PR2）、各 skill への model 宣言の一括付与（実測後）。

## 代替案と却下理由

- **モデル tiering を中核に据える**: 却下。cap / model 重みが非公開で効果が未実証、かつ精度リスクを伴う。オーナー方針（精度優先・汚染防止優先）に反する。補助レバーに格下げ（決定 3）。
- **文脈を一律に切り詰める（aggressive 圧縮）**: 却下。聖域（安全・なぜ）まで削ると手戻りで逆に高くつく。lossy は検知層付きで限定適用（決定 1-6）。
