# ADR-0010: 思考OS の2層構造（L0/L1）と配布・還流メカニズム

## ステータス

承認済み（2026-04-20）。一部 Superseded by ADR-0013（2026-04-28）:
- 2 層構造（L0 + L1） → 3 層構造（L0 + L1 + L2）
- PJ 配下 thinking.md の v1.0 廃止 → 取り下げ、L2 brain として永続化
- 命名 `neotion/` → `brain/`

配布・還流メカニズムの全体設計、`@import` による DRY 物理強制、L0 配布／L1 個人 SoT の方針は ADR-0013 でも継承される。

## 背景

ADR-0007 で thinking.md を「人に紐づく入れ替え可能な思考OS」と位置づけ、「将来的に thinking-os-template をスタンドアロン版として別リポで提供し、sidekick へのファネルとする構想」を明記した。

その後の運用で、思考OS が論理的には「人スコープ」でありながら、物理的には各 PJ の `.claude/rules/thinking.md` に独立コピーされている乖離が顕在化した。具体的には:

- PJ A で昇格した判断原則が PJ B に反映されない（ユーザー1人で複数 PJ を回す場合の典型）
- 3件ルール（同趣旨 feedback が3回溜まったら昇格検討）が PJ 単独でしか発動しない
- 思考OS の「PJ をまたいで成長する」性質が構造で保証されていない
- OSS 新規ユーザーは thinking.md をゼロから育てる必要があり、初期立ち上がりが重い

加えて、下流 PJ の気づきを sidekick 本体に還流する経路（reverse sync）も、現状は人間の手動判断のみで仕組み化されていない（MEMORY.md Backlog 論点D）。

## 検討内容

### 配布と還流のメカニズム分離

| 軸 | 方向 | 目的 |
|---|---|---|
| 配布 | 上流（脳tion/ccs）→ ホーム → PJ | 完成形の思考OSを新規ユーザーに即戦力で渡す |
| 還流 | PJ → ホーム → 上流（ccs PR） | 個人・PJ の気づきを集約し、汎用化したものを還流する |

両方が必要。配布だけでは個人進化が止まり、還流だけでは新規ユーザーがゼロから組み立てる羽目になる。ccs の思想（adopt-update + reverse sync）は両方を持つ構造で、思考OSもこの設計に乗せるのが一貫する。

### 階層構造の選択肢

| 選択肢 | メリット | デメリット |
|--------|---------|-----------|
| A: PJ 配下に thinking.md を物理コピー（現状） | シンプル。Claude Code の自動ロード対象に入る | PJ をまたいで成長しない。個人進化が分散する |
| B: 中央集約のみ（`~/.claude/rules/thinking.md` 1本） | 集約は完了。PJ を跨いで効く | 新規ユーザーにゼロから作らせる。配布導線なし |
| C: git submodule で専用リポ | バージョン管理厳密。履歴残る | 仕組みが重い。非エンジニア導入困難 |
| **D: L0（共通ベース）+ L1（個人差分）の2層構造＋ @import 配布（採用）** | 配布と個人進化を両立。DRY を物理強制（L1 = L0 + 差分） | 層が2つに増える。adopt-update 相当の仕組みをホーム側にも展開する必要あり |

### L0 リポの独立性

| 選択肢 | メリット | デメリット |
|--------|---------|-----------|
| A: 脳tion 専用リポとして独立 | ブランドが立つ。sidekick なしで単体利用可能。マーケ効果大 | 2リポ運用の負担 |
| **B: 過渡期は ccs 同梱の `neotion/` ディレクトリ、将来独立（採用） | 70%で動ける。一体運用から段階移行 | ブランド確立が遅れる |

### PJ 側 thinking.md の扱い

| 選択肢 | メリット | デメリット |
|--------|---------|-----------|
| A: 即廃止し、すべて `@~/.claude/rules/thinking.md` import に切替 | 構造が純粋 | 破壊的変更。major bump 必要 |
| **B: v1.0 target で段階廃止、それまで両対応（採用） | 下流 PJ への配慮 | 過渡期のコード複雑化 |
| C: 恒久的に両対応 | 互換性最大 | 「層の分離」の価値が薄れる |

## 決定

### 1. 思考OS は L0 + L1 の2層構造とする

```
L0（共通ベース）
  配布元: 脳tion リポ（将来独立）/ 過渡期は ccs 同梱 `neotion/`
  取り込み先: `~/.claude/ccs/thinking.md`（adopt-update で pin バージョン管理）

L1（個人差分）
  配置: `~/.claude/rules/thinking.md`
  構造: 冒頭に `@~/.claude/ccs/thinking.md` で L0 を import、以降は個人追加分のみ
  SoT: ここが人スコープ思考OSの真のSoT

PJ 側
  各 PJ の CLAUDE.md が `@~/.claude/rules/thinking.md` で L1 を import
  PJ 配下の `.claude/rules/thinking.md` は v1.0 で廃止
```

L1 = L0 + 差分、という構造を @import で物理強制する。これにより DRY を構造で保証する。

### 2. 配布と還流の2メカニズムを併存させる

- **配布**: `/adopt-sidekick-update` の思想をホーム配下にも拡張（L0 更新時、ホーム側で取り込み判断）
- **還流**: 各 PJ agent-memory を横串スキャンする `brain-reflow` 的スキルを `~/.claude/skills/` に配置。3件ルールでクラスタ検出 → L1 昇格候補を提示。さらに汎用性あるものは L0（ccs リポ）への PR に進む

### 3. 還流タグを細分化する

現行の `[思考OS還流]` / `[固有]` を以下に置き換える:

- `[L0候補]`: 誰にでも有用な汎用判断軸（ccs 還流候補）
- `[L1固有]`: オーナー個人の文脈・好み・失敗経験を含む判断軸（個人 thinking.md 昇格のみ）

「L0候補」の判定基準: **オーナー固有の文脈が書かれていない原則**（主観だが、再読時に他者にも通じるかが目安）。

### 4. L0 リポは過渡期 ccs 同梱、v1.1+ で独立を検討

v0.7〜v0.9 は ccs 同梱 `neotion/` ディレクトリ、v1.0 で PJ thinking.md 廃止と合わせて独立リポ化の可否を再判断する。

### 5. PJ 配下 thinking.md は v1.0 で廃止、それまで両対応

過渡期（v0.7〜v0.9）は `/setup` で以下のどちらかを選ばせる:

- (a) 現状通り PJ 配下に thinking.md コピー（team 利用向け、互換性維持）
- (b) `@~/.claude/rules/thinking.md` import のみ（個人・複数PJ利用向け、推奨）

v1.0 で (b) にフォールバック統一する破壊的変更を行う（ADR-0011 相当で切る想定）。

## 理由

### ccs の思想との整合

ccs は「リファレンス集から各 PJ が pick up する」思想。思考OS もこのカスケードに乗せるのが最も一貫する。

### 既存活用ファースト（ベーステンプレは拡張ファースト）

L0 の adopt-update は既存の `/adopt-sidekick-update` 機構をそのまま転用可能。横串スキャンは auto-memory が既に `~/.claude/projects/` に集約されている事実を利用するだけで、追加インフラ不要。

### DRY の物理強制

L1 = L0 + 差分、を @import で強制することで、L0 のルールが L1 に重複する事故を構造で防ぐ。

### 70% で動く

Phase 1（脳tion ディレクトリ切り出しと L0/L1 区別）だけで最小価値が出る。還流メカニズム（横串スキャン）は Phase 2 以降で後付け可能。

### 非エンジニア3クリック

OSS 新規ユーザーは「脳tion の L0 を clone → ホーム配下に配置 → 各 PJ CLAUDE.md に1行追加」で即使える。育てる過程は使いながら進む（ADR-0007 の「テンプレートのまま動かし、weekly-inventory で自然に育てる」決定と整合）。

## 却下した案の理由

- **中央集約のみ（選択肢B）**: 新規ユーザーにゼロから作らせる導線は OSS として弱い。脳tion の完成形を配布する価値を捨てることになる
- **submodule（選択肢C）**: 仕組みが重く、非エンジニアの導入を阻害する。ADR-0008 で auto-memory に寄せた「標準機能追従」の方針とも逆行する
- **L0 リポ即独立（選択肢A）**: 2リポ運用の負担が先行して増える。70%リリースの原則に反する
- **個人 ccs リポを 3リポ目として持つ案**: 「個人専用 ccs フォーク」で全カスタム（thinking.md / skills / hooks / rules）を一括管理する案は採らない。理由は3つ:
  1. ccs upstream の追従 sync を 3リポ目に作ることになり、ADR-0006 が解いた「フォーク先での upstream 取り込み問題」を再発させる
  2. Claude Code は `~/.claude/` をユーザー級の標準配置としてサポートしており、リポ単位ではなく**レイヤー単位**で個人差分を持つ方が標準機能追従の方針（ADR-0008）と整合する
  3. 個人専用 skill/hook の具体ニーズが現時点で 3件未満であり、先取り設計しない方が 70%リリース原則と整合する

## 影響

### 変更が入るファイル・機能

- `.claude/rules/thinking.md`（sidekick 配布版）: 冒頭に L0/L1 概念の説明を追加、過渡期の両対応明記
- `CLAUDE.md §1`: L0/L1 の関係を参照記述、`@~/.claude/rules/thinking.md` import の導線
- `/setup` スキル: (a)/(b) の選択肢追加
- `/adopt-sidekick-update` スキル: L0 取り込みのホーム側適用を検討
- `/close-chat`, `/weekly-inventory` スキル: 還流タグを `[L0候補]` / `[L1固有]` に更新
- `knowledge-map.md`: L0/L1 階層を追記
- 新規: `~/.claude/skills/brain-reflow`（横串スキャンスキル、Phase 2 以降）

### バージョン方針

- Phase 1 実装は v0.7.0（minor bump、機能追加）
- PJ thinking.md 廃止は v1.0.0（major bump、破壊的変更）

### 今後注意すべき点

- L0 と L1 の線引き（汎用 vs 個人）は主観判断。`[L0候補]` タグの運用次第で精度が変わる
- L0 更新で L1 が壊れないよう、adopt-update は pin + diff review が必要
- PJ thinking.md が残る過渡期は `@import` 優先順の定義が必要（存在すれば PJ 優先、なければホーム）
- `brain-reflow` の初版はシンプルな grep + 類似クラスタでよい。LLM ベースの類似判定は将来拡張
- **本ADRの射程は思考OS（thinking.md）に限る**。skills / hooks / 他の rules ファイル（database.md 等）の個人差分は対象外。auto-memory に個人専用カスタマイズが 3件以上溜まったタイミングで、別 ADR（Phase 2 相当）として `~/.claude/skills/`, `~/.claude/hooks/` 拡張を検討する

### 関連する今後の議論

- ADR-0007 の補強として位置づく（思考OSの物理配置を定義）
- 論点D（reverse sync 経路設計）は、この ADR の還流メカニズムに統合される
- v1.0 リリース時の移行ガイド作成が必要
